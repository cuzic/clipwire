ターン API)はまだ存在しない。本 PoC はラッパー試作

結合テスト(`tests/t9_3_persistent_context_poc.rs`)・ベンチマーク

## 項目1: stdout/stderr 捕捉の網羅性

- Date: 2026-11-03
- Command: `cargo test --test t9_3_persistent_context_poc poc_item1 -- --nocapture`
- ラッパーは、ターン実行中だけ自分自身の fd 1/2 を一時ファイルへ
  `os.dup2` で向け直す(`wrapper.py` の `run_turn`)。`dup2` はファイル
  記述子の**番号**が指す先を切り替えるだけなので、Python レベルの
  `print()`/`sys.stdout` だけでなく、同じ fd を継承したサブプロセスの
  出力、`os.write(1, ...)` による生の fd 書き込みも、同じ退避先に
  素通りで乗る。`contextlib.redirect_stdout` のような Python レベルの
  差し替えだけでは、サブプロセス・ネイティブ拡張の出力(pywinauto が
  想定するケース)を拾えないため採用しなかった。
- 検証: `print("from_print")` / `subprocess.run([sys.executable, "-c",
  "print('from_subprocess')"])` / `os.write(1, b"from_raw_fd\n")` /
  `print("from_stderr", file=sys.stderr)` を 1 ターンで実行し、すべてが
  レスポンスの `stdout`/`stderr` に含まれることを確認(実測:
  `stdout = "from_subprocess\nfrom_raw_fd\nfrom_print\n"`)。
- **既知の制約**: 3 系統の出力は、各ライターのバッファリング・flush
  タイミングによって**ソースコード上の順序と出力順序が一致しない**
  (実測でも `from_subprocess` が `from_print` より先に現れた)。
  pywinauto のログとユーザーコードの `print` を時系列で厳密に
  突き合わせる用途には、この捕捉方式だけでは順序保証がないことを
  明記する必要がある。
- Result: pass(欠落なし、順序保証なしという制約つき)。

## 項目1(続き): フレーミング分離の実装バグと EOF 検知の修正

2 回目の Opus レビューで、改訂3時点の実装・ADR 記述に 2 つの実質的な
欠陥が見つかった。いずれも `wrapper.py` を修正し、回帰テスト
(`tests/t9_3_persistent_context_poc.rs`)を追加して確認した(修正前の
コードに戻すと実際に失敗することも確認済み)。

- **【重大】プロトコル分離が「ターン外は常にログ側」になっていなかった**:
  改訂3時点の `wrapper.py` は、`run_turn` の `finally` で fd 1 を
  **プロトコル用パイプへ**戻していた(起動時に dup2 で退避した先が、
  まだプロトコル用パイプそのものだったため)。ADR §2 は「確認済み」と
  書いていたが、`poc_item1`/`poc_item2` のテストはどちらもターン内で
  完結する出力しか扱っておらず、「ターン中に起動したスレッドがターン
  後に書く」ケースを検証していなかった。
  - 修正: 起動直後に `os.dup2(2, 1)` で fd 1 を恒久的にログ側(fd 2 の
    送信先)へ向け直し、`run_turn` の `finally` もログ側に戻すように
    変更。
  - 回帰テスト: `poc_item1_late_write_after_turn_does_not_corrupt_next_turns_framing`。
    ターン1でバックグラウンドスレッドを起動し、fd 1 へ直接書き込ませる。
    修正前のコードに戻すと、ターン2の応答が
    `"late-background-write\n"` という生の文字列になり JSON パースに
    失敗することを確認済み。
- **【重大】ハング中のターンは EOF に気づけない**: stdin の読み取りを
  ターン実行スレッド自身が行う設計だと、ターンがハング中(pywinauto の
  モーダルダイアログ待ち等)は EOF(サーバプロセスの終了)に気づけず、
  再起動後も `JobRegistry` の「席」を握り続ける(詳細は
  ADR-0013 §3・Consequences 参照)。
  - 修正: stdin の読み取りを専用スレッドに移し、EOF を受けたら
    メインスレッドの状態に関わらず `os._exit()` で即座に終了する。
  - 回帰テスト: `poc_eof_during_a_hung_turn_still_exits_promptly`。
    30 秒かかる(ハングを模した)ターンを送った直後に stdin を閉じ、
    ラッパーが(30 秒待たずに)5 秒以内に自発的に終了することを確認。
- **【中】上記2つの回帰テストが時間待ち(0.3秒/0.5秒/0.3秒)に依存しており、
  CI が混んでいると誤検出する(3回目のレビューで指摘)**: 時間待ちでは、
  想定より遅延が起きた場合に「ハング中ではなくまだターンに入る前」や
  「ターン1がまだ応答する前」に次の操作をしてしまい、テストの意図(フレー
  ミングが壊れないこと/ハング中に EOF を検知すること)を実際には検証でき
  なくなる。
  - 修正: 固定の sleep をやめ、マーカーファイルの存在をポーリングする
    同期に変更。ターン中の stdout/stderr はそのターンの JSON 応答にしか
    現れない(外部へライブ中継されない)ため、ファイルで合図する。
    late-write テストは、テスト側がターン1の応答を実際に受け取った後に
    「書いてよい」ファイルを作り、バックグラウンドスレッドはそれが
    現れるまで待ってから書く(= fd 1/2 の復元が確実に完了した後に書く
    ことを保証)。EOF テストは、ターンの先頭でまず(sleep に入る前に)
    マーカーファイルを作り、テスト側はそれを見てから stdin を閉じる。
- **【重大・Windows 固有】stdin を別スレッドでブロッキング読み取りして
  いる状態でターン内から subprocess を起動すると、Windows でだけ必ず
  ハングする**: 上記2つの回帰テストを追加して Windows CI で走らせた
  ところ、新しい2テスト自体は緑だったが、既存の
  `poc_item1_stdout_capture_covers_subprocess_and_raw_fd_writes`
  (ターン内で `subprocess.run(...)` を呼ぶテスト)が 10 秒タイムアウト
  で失敗した(run 41765566207)。原因の切り分けに計4回のCI往復を要した。
  - 試行1(効果なし): `_PROTOCOL_STDOUT_FD`・`saved_stdout_fd`/
    `saved_stderr_fd`・`out_fd`/`err_fd` が、PEP 446 の non-inheritable
    既定に反して Windows でサブプロセスへ継承されるのではないかと考え、
    `os.set_inheritable(fd, False)` を全てに明示適用。再実行
    (run 41766569527)でも同じ症状で失敗。
  - 試行2(効果なし): fd 1 の恒久リダイレクト先を「`os.dup2(2, 1)` で
    fd 2 と同じ送信先へ**別名付け**する」実装自体を疑い、fd 2 とは
    独立した **devnull** に変更。再実行(run 41767347409)でも同じ症状
    で失敗。
  - 試行3(効果なし): stdin の読み取り方法を `sys.stdin`(`io.TextIOWrapper`
    の行バッファリング)から fd 0 への `os.read()` 直接呼び出しに変更。
    再実行(run 41767969155)でも同じ症状で失敗。
  - **診断的切り分け(効果あり)**: 「別スレッドで stdin をブロッキング
    読み取りしている」設計自体を疑い、スレッドを完全に無効化(EOF 検知
    の要件を諦めて単一スレッドの素朴な読み取りに戻す)した診断用コミット
    を投入(run 41768378160)。**この時だけ
    `poc_item1_stdout_capture_covers_subprocess_and_raw_fd_writes` が緑に
    なった**(無効化した機能に依存する `poc_eof_during_a_hung_turn_...`
    は予想通り失敗)。これにより、「別スレッドが stdin へのブロッキング
    読み取りで待機している状態で、別のスレッドから `subprocess` を起動
    する」という組み合わせ自体が Windows で問題を起こすと断定した
    (`sys.stdin`/`os.read()` のどちらでも、fd1/fd2 の実装をどう変えても
    再現したため、読み取り方法や fd の別名付けは原因ではなかった。OS/
    CPython API レベルの正確な機序は特定できていない)。
  - **最終的な修正**: 終了検知の手段を「stdin を読む」ことから完全に
    切り離し、**親プロセス(サーバ)の PID 生存を sleep ベースで
    ポーリングする**方式に変更した(ADR-0013 §3 改訂6 参照)。
    `time.sleep()` はブロッキング I/O ではなく GIL も解放するため、同様
    の問題を起こさない。これにより `poc_eof_during_a_hung_turn_...` の
    シミュレーション手順も変更が必要になった: ラッパーの実際の OS 上の
    親プロセスが「サーバ」である必要があるため、テストプロセス自身を
    親にする代わりに、使い捨ての中継プロセス(ラッパーを起動して待つ
    だけの python スタブ)を挟み、テストはその中継プロセスだけを
    kill+reap して「サーバが死んだ」状況を模す(テストプロセス自身は
    生き続けて結果を観測できる)。この修正後の run(後述)で windows
    ジョブが緑になった。
  - **【重大】上記の修正(親PID生存ポーリング)には、2回目の独立した
    Opus レビューで launcher 構成に対する欠陥が指摘された**:
    `script_file` の `interpreter`(例 `["python"]`)が、venv の
    `python.exe`(リダイレクタ)・`uv run`・py ランチャーのような
    「ラッパーを子として起動して待つだけの中継プロセス」を経由する
    構成では、ラッパーの OS 上の親は**サーバではなく中継プロセス**に
    なる。サーバが死んでも中継プロセスは死なない(Job Object が無く
    道連れにならない)ため、`getppid()` ベースの監視では永久にサーバの
    消滅を検知できない。さらに、上記テストの `spawn_behind_stub` は
    「中継プロセスの方を kill する」構成になっており、本番で起きる
    「サーバが死に、中継プロセスは生き残る」ケースとは**逆**を検証して
    いたため、この欠陥を検出できない構造だった。
  - レビューからの仮説(未検証): Windows の `subprocess` は
    `stdin=None` のとき `GetStdHandle(STD_INPUT_HANDLE)` を子の stdin
    として渡すため、子プロセスを起動するたびに「読み取り中のパイプ
    そのもの」(= fd 0 の番号)に触れる。別スレッドがまさに fd 0 を
    `ReadFile` でブロッキング読み取り中だと、Windows の同期 I/O の
    直列化により衝突する。試行1〜3(上記)はいずれも fd 1/fd 2 側か
    読み取り方法を変えたもので、**fd 0 の番号そのもの**は変えていな
    かったため、この仮説と矛盾しない。
  - **最終的な修正(改訂7)**: fd 1 に適用した devnull 化と同じパターンを
    fd 0 にも適用した。起動直後に `_PROTOCOL_STDIN_FD = os.dup(0)`
    (non-inheritable)でプロトコル入力を退避し、fd 0 の番号自体を
    `os.dup2(os.open(os.devnull, os.O_RDONLY), 0)` で恒久的に devnull へ
    向け直す。ラッパー内の読み取りは `_PROTOCOL_STDIN_FD` から行い(専用
    スレッド、EOF で `os._exit()`)、ターン内で起動されるサブプロセスは
    fd 0(devnull)を継承するだけで、読み取り中のパイプには一切触れない。
  - **結果**: この変更後、run 41771067481 で windows ジョブを含め
    全6テストが緑になった。これにより「親 PID 生存ポーリング」(改訂6)
    を完全に撤回し、本来の **stdin EOF 方式**に戻せた。EOF はパイプの
    書き込み側を持つプロセス(サーバ)だけに依存するため、`interpreter`
    に何段の中継プロセスが挟まっていても、サーバが死ねば確実に起きる。
  - 追加した回帰テスト:
    - `poc_eof_propagates_through_an_intermediate_relay_process`:
      中継プロセス(スタブ)を**生かしたまま**、テスト側のパイプだけを
      閉じてもラッパーが終了することを確認(launcher 構成の直接的な
      検証。改訂6のテストが検証できていなかったケース)。
    - `poc_subprocess_from_background_thread_between_turns_does_not_hang`:
      2回目のレビューで指摘された「ハングの条件はターンの外でもまだ
      成立する」(ターン間はメインスレッドが stdin を読んで待っている
      ため)という懸念に対する回帰テスト。前のターンが残したバック
      グラウンドスレッドがターンの外で subprocess を起動しても、次の
      ターンがハングしないことを確認。

## 項目3: アイドルタイムアウト・絶対寿命と Job Object の関係 — **ブロッキングな発見**

- Date: 2026-11-03
- 調査方法: コード読解(`src/runner/windows.rs`, `src/runner/mod.rs`)。
  実行は伴わない。
- **Windows の Job Object 統合(T4.4)は、このコードベースにまだ実装
  されていない**。`src/runner/windows.rs` の `OsProcessGroup` は
  スタブで、`spawn_in_group` は `command.spawn()` をそのまま呼ぶだけ、
  `terminate()` は何もせず `Ok(())` を返し、`members()` は
  `Unsupported` エラーを返す。`src/runner/mod.rs:484-495` の
  `JobHandle::terminate()` も、Windows では Job 経由ではなく
  **直接の子プロセスにのみ** `child.kill()` を呼ぶ実装になっている
  (コメントに "T4.4 owns Job Objects. Until then Windows deliberately
  retains the old std::process fallback and can only kill the direct
  child." と明記)。`docs/tasks/README.md` の T4.1/T4.4 行も「未着手
  (Windows 実機・実装待ち)」。
- ADR-0013 §3 は「永続コンテキストも Job に入れて `TerminateJobObject`
  で確実に子孫も倒すのか」を PoC 確認項目としていたが、**比較対象の
  Job Object 統合自体が存在しないため、この PoC では確認できない**。
  pywinauto のような UI 自動化は対象ウィンドウを持つプロセス(孫)を
  見つけて操作するだけで新規プロセスを多数起動するとは限らないが、
  ラッパー自身が exec で起動したサブプロセス(項目1の検証と同様)が
  残存した場合、現状の Windows 実装では **アイドルタイムアウト/絶対
  寿命でラッパーを `kill()` しても、ラッパーが起動した孫プロセスは
  道連れにならず残り続ける**。
- **実機 `dragonflyg4` での直接確認**(2026-11-03、コード読解だけでなく
  実際に再現): Python の親プロセスが子プロセス(60 秒 sleep する別
  Python)を起動した状態を作り、親の PID のみを `Stop-Process -Force`
  で終了(= 現在の Windows 版 `JobHandle::terminate()` と同じ「直接の
  子だけを kill する」操作)。結果、`grandchild alive AFTER kill
  (LEAK if true): True` —— 孫プロセスは生き残った(手動で後片付け)。
  親は確かに消えた(`parent alive AFTER kill: False`)。これは上記の
  コード読解による予測を実機で裏付けるもので、「今は Job Object という
  選択肢自体が無く、`child.kill()` では孫が実際に漏れる」ことを
  推測ではなく再現された事実にしている。
- **当初の結論(2026-11-03)**: 項目3 は「未検証」ではなく「前提が崩れて
  いる」。永続コンテキストの本実装は (a) T4.4 の完了を前提にする、
  または (b) ラッパー自身が子孫 PID を自己追跡する、のいずれかを選ぶ
  必要があり、(a) を既定方針とした。
- **【結論変更】Opus レビューで判明(2026-11-03)**: (a) を本実装の
  前提にするのは、同じ「Windows では子孫を倒せない」制約を抱えたまま
  T5.1(timeout)・T6.2(`--detach`/`kill`)が既に出荷されていることと
  不整合。さらに Job Object は pywinauto の対象アプリ(既に起動済みの
  アプリ、COM 経由で別ホストから起動されるプロセス等、ラッパーの子孫
  でない場合が多い)に対して必要条件でも十分条件でもなく、
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を使えば操作対象として残したい
  アプリまで落ちる副作用もある。したがって T4.4 を待っても「終了処理
  が正しくなる」とは言えない。方針を「直接の子 kill で出荷し、孫
  プロセスの残存は T5.1/T6.2 と同じ既知の制約として明記する」に変更
  した(T4.4 完了時に自動的に改善される)。詳細は ADR-0013 §3
  (改訂3)参照。

## 項目4: `Concurrency::Reject` と永続コンテキストの相互排他の実装場所

- Date: 2026-11-03
- 調査方法: コード読解(`src/jobs.rs:176-220`)。実行は伴わない。
- `Concurrency::Reject` は `JobRegistry::start`(`src/jobs.rs:176`)の中で、
  **`JobRegistry` 自身が保持する `jobs: HashMap` を `job.target == target`
  で線形走査する**ことで実装されている。ロックも `JobRegistry` 内部の
  `Mutex` 止まりで、他のレジストリの状態は一切見えない。
- ADR-0013 は `PersistentContextRegistry` を `JobRegistry` とは独立した
  別レジストリにすると明記している(`Runner::spawn` の `Stdio::null()`
  前提と非終端プロセスの扱いが競合するため)。この設計のままだと、
  **通常の `exec`(`JobRegistry::start` 経由)と永続コンテキストの起動/
  ターンは、互いの存在を一切知らない 2 つの独立したロック・マップの下で
  並走できてしまう**。`Concurrency::Reject` を両者のどちらの内部に実装
  しても、もう一方からは見えない。
- **実装場所の当初案(2026-11-03 時点)**: どちらのレジストリにも実装を
  押し込まず、両方を呼び出す前段(`src/server/exec.rs` の exec
  ディスパッチハンドラ)に、ターゲット名をキーにした共有の「使用中」
  集合(`Arc<Mutex<HashSet<String>>>`)を新設する案。
- **【撤回】Opus レビューで欠陥が判明(2026-11-03)**: この案は
  `JobRegistry::open` が起動時に復元する `Orphaned`(再起動前に生きて
  いた子)の状態が見えず、サーバ再起動直後に通常 `exec` 側は弾かれる
  のに永続コンテキスト側は素通りする非対称が生じる。また `finish`/
  `kill`/`Lost` 遷移・detach・panic など `JobRegistry` のライフサイクル
  全経路に解放フックを重複して持つ必要があり、片方だけ更新されると
  集合がリークしたまま 409 を返し続けるか相互排他そのものが壊れる、
  という二重管理の問題を抱える。代わりに、永続コンテキストが
  `JobRegistry::start` で通常の job と同じ「席」を取る方式に変更した
  (前提として `persistent: true` ターゲットの単発 `exec` を禁止する)。
  詳細は ADR-0013 §3(改訂3)参照。

## 項目5: 毎ターンのハッシュ再検証コスト

- Date: 2026-11-03(デバッグビルド)、2026-11-03(release ビルドで再測定。
  改訂3。Opus レビューで「デバッグビルドの数字は本番の値ではない」と
  指摘された)
- Command: `cargo test --bin clipwire store::tests::poc_t9_3_item5 --
  -- --ignored --nocapture`(デバッグ)/ `cargo test --release --bin
  clipwire store::tests::poc_t9_3_item5 -- --ignored --nocapture`
  (release)
- 実機相当の件数(dragonflyg4 の `registered.toml` は 1571 件、T9.0
  evidence 参照)で、既存の再検証経路そのもの(`Store::verified_target`
  → `load_target_map` → `verify_approval`)を 20 回呼んで平均コストを
  測定。
- **実測**(`registered.toml`、220,863 バイト、1571 エントリ):
  - デバッグビルド(`opt-level=0`): `verified_target` 1 回あたり平均
    **約 317ms**。内訳: `fs::read_to_string` = 131〜134µs、
    `toml::from_str` = 288〜356ms、`fs::metadata(...).modified()` =
    26〜39µs。
  - **release ビルド(`opt-level=3, lto=true`。本番と同じプロファイル)**:
    `verified_target` 1 回あたり平均 **約 19.2ms**(20 回平均、合計
    383.6ms)。内訳: `fs::read_to_string` = 229µs、`toml::from_str` =
    **11.4ms**、`fs::metadata(...).modified()` = 19µs。
  - デバッグ比で **約 16.5 倍速い**。支配的コストは release でも変わらず
    `toml::from_str` だが、絶対値は「明確に対話性を損なう 300ms」から
    「十数 ms」に下がる。
- **結論(改訂3で変更、改訂4でさらに変更)**: release ビルドでの実測
  (約 19ms)は、PoC 時点で想定していた「応答性を明確に損なう 300ms」
  ほど深刻ではない。pywinauto の 1 ターン(要素探索・UIA 呼び出し)は
  通常これより 1 桁以上長いと考えられ、mtime ゲート(`registered.toml`
  の再パースを、変化がなければ省略する仕組み)を入れる効果は限定的。
  キャッシュの導入は、それ自体が新しい不具合の入り口になる(Windows
  での file identity 取得を誤る、比較キーの一部を落とす等)ため、
  **最初の実装ではゲートを入れず、`exec` と同じ素朴な全件再検証のまま
  出荷し、実測で実際に応答性を損なうと判明してから追加検討する**
  (ADR-0013 改訂4。改訂3時点では「採用はそのまま推奨」としていたが、
  Opus レビューで「ゲート自体に害はない、は言い過ぎ」と指摘され撤回)。
  この 19ms は **Linux の開発機での値**であり、実機 Windows
  (`dragonflyg4`。ウイルス対策のリアルタイムスキャンが
  `registered.toml` の読み込みに掛かる可能性がある)での実測はまだ
  ない(本実装着手前に取る。ADR-0013 Status 参照)。
- **ゲートを将来追加する場合の正しさに関する指摘(Opus レビュー、
  改訂3で反映、改訂4でも有効)**: 当初の設計(mtime が変わっていなければ
  (a) `registered.toml` の再パースと (b) `approved/<hash>.json` の検証
  の両方を省略する)は、`approved/<hash>.json` の削除・改ざん・部分
  書き込み(ADR-0010 §3 が「改ざん・部分書き込みの検出」と位置づける
  検査)を検知できなくする退化を招く。(b) は数 KB の読み込み + sha256
  で µs〜数十 µs にすぎず支配的コストではないため、**ゲートを追加する
  場合でも対象は (a) のみに限定し、(b) は mtime に関わらず毎ターン
  必ず行う**。また mtime 単独ではなく `(ファイル identity, size,
  mtime)` の組を `!=` で比較すること、mtime はロック内・パース前に
  取得することも、将来ゲートを追加する際の要件として ADR-0013 §3 に
  記録した。
- **付随して判明した既存コードの観察(本 PoC の対象外。別途記録する
  価値がある)**: 通常の単発 `exec` も `prepare()`(`src/server/exec.rs`)
  経由で毎回 `verified_target` を呼んでおり、この実測コスト(release
  でも約 19ms、デバッグでは約 300ms)を既に払っている。`prepare` は
  同期関数として async ハンドラから直接呼ばれており(`spawn_blocking`
  されていない)、呼び出しのたびに tokio ワーカースレッドをその時間
  ブロックする。永続コンテキスト固有の問題ではなく、既存の `exec`
  経路全体に関わる観察。

## 付記: ベンチマークテストの CI 安定性

`store::tests::poc_t9_3_item5_verified_target_cost_against_1571_entries`
は 20 回 x 約 300ms の CPU 束縛な `toml::from_str` を連続実行するため、
デフォルトの `cargo test` 並列実行下で他のタイミング依存テスト
(`ac_t6_1_5_*`・`ac_t4_5_6_*` 等)を不安定化させることが、push 後の
CI(run 41751250415、`linux` ジョブのみ失敗)と、ローカルでの複数回
再現で確認された。`#[ignore]` を付けて通常の `cargo test`/CI から外し、
`cargo test -- --ignored` での単独実行専用にした(測定結果そのものは
変わらない。不安定化の原因が測定対象ではなく並列実行の資源競合である
ことをローカルで確認済み)。

## 全体のまとめ(AC-T9.3.2 への入力。改訂7で更新)

- 項目1・2: 設計方針どおりに動くことを実プロセス・実機・Windows CI で
  確認した(項目1は出力順序の保証がないという制約つき)。プロトコル
  応答・入力を fd 1・fd 0 から分離し、両方の番号を恒久的に devnull へ
  向け直す(改訂3時点では未実装、改訂7で fd 0 側も追加)修正を
  `wrapper.py` に適用し、ターン後の遅延書き込みがフレーミングを壊さ
  ないこと、ハング中のターンでもサーバ終了(stdin EOF)を検知して即座に
  終了すること、`interpreter` が中継プロセスを経由していても検知できる
  こと、ターンの外でのバックグラウンドスレッドからの subprocess 起動が
  妨げられないことを、いずれも回帰テストで確認した。この過程で
  Windows 実機でだけ再現する実在のハングを発見し、4〜5回のCI往復と
  2回の独立レビューを経て原因(fd 0 の番号への同期I/O競合)を特定・
  修正した(項目1(続き)参照)。
- 項目3: Windows Job Object 統合(T4.4)がまだ実装されていないことが
  判明したが、Opus レビューで「これを理由に本実装を止めるのは T5.1/
  T6.2 の扱いと不整合」「Job Object は pywinauto の対象アプリに
  必要条件でも十分条件でもない」と指摘され、T4.4 待ちにしない方針へ
  改訂した(ADR-0013 §3)。「直接の子を kill すれば受付口が止まる」
  という当初の根拠も、中継プロセスを経由する構成では成り立たないと
  判明し、「stdin を閉じてラッパー自身が EOF で終了する」を受付口を
  止める実際の手段として書き直した。
- 項目4: 当初案(exec ディスパッチ層への共有集合)は `JobRegistry` の
  `Orphaned` 復元状態が見えない・解放経路が二重管理になるという欠陥が
  Opus レビューで判明し、永続コンテキストが `JobRegistry::start` で
  「席」を取る方式に改訂した。前提として `persistent: true` ターゲット
  の単発 `exec` を禁止する。この「席」方式に残っていた kill の入口・
  `finish` のステータス対応・ログ API の振る舞いという未決の API 設計
  (2回目のレビューで判明)は改訂5で決定済み。
- 項目5: デバッグビルドでの実測(約 300ms)は release ビルド(Linux
  開発機)では約 19ms に下がり、pywinauto の1ターンより1桁以上短いと
  考えられるため、mtime ゲートは**最初の実装には入れない**ことに
  した(改訂3時点では「任意の最適化として採用」としていたが、
  「ゲート自体に害はない、は言い過ぎ」と指摘され撤回)。将来ゲートを
  追加する場合の設計要件(対象を `registered.toml` の再パースのみに
  限定、`approved/<hash>.json` 側は毎ターン必ず検証)は ADR-0013 §3 に
  記録した。実機 Windows での実測はまだない(Consequences 参照)。
- 結論として、PoC(T9.3)自体は完了し、改訂2〜6 の Decision にはそれぞれ
  独立した Opus レビュー(計4回)で複数の実質的な欠陥が見つかったため、
  ADR-0013 を改訂7まで Decision を再修正した。4回目のレビューで新しい
  重大な欠陥が見つからなくなったため、Status を Accepted に進めた。
  本実装着手時に確認すべき残りの事項は ADR-0013 の「Consequences」節を
  参照。
