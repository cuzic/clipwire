# T9.3 evidence — ADR-0013 永続実行コンテキスト PoC

対象: ADR-0013 末尾の PoC 項目 1〜5。本実装(`PersistentContextRegistry`・
ターン API)はまだ存在しない。本 PoC はラッパー試作
(`docs/tasks/evidence/poc/t9.3/wrapper.py`)と、Rust 側の実プロセス
結合テスト(`tests/t9_3_persistent_context_poc.rs`)・ベンチマーク
(`src/store.rs` の `store::tests::poc_t9_3_item5_...`)で検証した。

2026-11-03 に書いた項目3・4・5 の当初の結論には、独立した Opus
レビューで複数の実質的な欠陥が見つかった(デバッグビルドの数字を
本番値として扱っていた、mtime ゲートが承認完全性検査を弱めてしまう、
共有集合案が `JobRegistry` の復元状態と二重管理になる、T4.4 待ちが
他タスクの扱いと不整合)。各項目に当初の結論と、2026-11-04 のレビュー
反映後の結論の両方を残す(ADR-0013 改訂3 で Decision を再修正)。

## 項目1: stdout/stderr 捕捉の網羅性

- Date: 2026-11-03
- Command: `cargo test --test t9_3_persistent_context_poc poc_item1 -- --nocapture`
- ラッパーは、ターン実行中だけ自分自身の fd 1/2 を一時ファイルへ
  `os.dup2` で向け直す(`wrapper.py` の `run_turn`)。`dup2` はファイル
  記述子の**番号**が指す先を切り替えるだけなので、Python レベルの
  `print()`/`sys.stdout` だけでなく、同じ fd を継承したサブプロセスの
  出力、`os.write(1, ...)` による生の fd 書き込みも、同じ退避先に
  素通りで乗る。`contextlib.redirect_stdout` のような Python レベルの
  差し替えだけでは、サブプロセス・ネイティブ拡張の出力(pywinauto が
  想定するケース)を拾えないため採用しなかった。
- 検証: `print("from_print")` / `subprocess.run([sys.executable, "-c",
  "print('from_subprocess')"])` / `os.write(1, b"from_raw_fd\n")` /
  `print("from_stderr", file=sys.stderr)` を 1 ターンで実行し、すべてが
  レスポンスの `stdout`/`stderr` に含まれることを確認(実測:
  `stdout = "from_subprocess\nfrom_raw_fd\nfrom_print\n"`)。
- **既知の制約**: 3 系統の出力は、各ライターのバッファリング・flush
  タイミングによって**ソースコード上の順序と出力順序が一致しない**
  (実測でも `from_subprocess` が `from_print` より先に現れた)。
  pywinauto のログとユーザーコードの `print` を時系列で厳密に
  突き合わせる用途には、この捕捉方式だけでは順序保証がないことを
  明記する必要がある。
- Result: pass(欠落なし、順序保証なしという制約つき)。

## 項目2: 改行区切り JSON フレーミングの安定性

- Date: 2026-11-03
- Command: `cargo test --test t9_3_persistent_context_poc poc_item2 -- --nocapture`

## 項目3: アイドルタイムアウト・絶対寿命と Job Object の関係 — **ブロッキングな発見**

- Date: 2026-11-03
- 調査方法: コード読解(`src/runner/windows.rs`, `src/runner/mod.rs`)。
  実行は伴わない。
- **Windows の Job Object 統合(T4.4)は、このコードベースにまだ実装
  されていない**。`src/runner/windows.rs` の `OsProcessGroup` は
  スタブで、`spawn_in_group` は `command.spawn()` をそのまま呼ぶだけ、
  `terminate()` は何もせず `Ok(())` を返し、`members()` は
  `Unsupported` エラーを返す。`src/runner/mod.rs:484-495` の
  `JobHandle::terminate()` も、Windows では Job 経由ではなく
  **直接の子プロセスにのみ** `child.kill()` を呼ぶ実装になっている
  (コメントに "T4.4 owns Job Objects. Until then Windows deliberately
  retains the old std::process fallback and can only kill the direct
  child." と明記)。`docs/tasks/README.md` の T4.1/T4.4 行も「未着手
  (Windows 実機・実装待ち)」。
- ADR-0013 §3 は「永続コンテキストも Job に入れて `TerminateJobObject`
  で確実に子孫も倒すのか」を PoC 確認項目としていたが、**比較対象の
  Job Object 統合自体が存在しないため、この PoC では確認できない**。
  pywinauto のような UI 自動化は対象ウィンドウを持つプロセス(孫)を
  見つけて操作するだけで新規プロセスを多数起動するとは限らないが、
  ラッパー自身が exec で起動したサブプロセス(項目1の検証と同様)が
  残存した場合、現状の Windows 実装では **アイドルタイムアウト/絶対
  寿命でラッパーを `kill()` しても、ラッパーが起動した孫プロセスは
  道連れにならず残り続ける**。
- **実機 `dragonflyg4` での直接確認**(2026-11-03、コード読解だけでなく
  実際に再現): Python の親プロセスが子プロセス(60 秒 sleep する別
  Python)を起動した状態を作り、親の PID のみを `Stop-Process -Force`
  で終了(= 現在の Windows 版 `JobHandle::terminate()` と同じ「直接の
  子だけを kill する」操作)。結果、`grandchild alive AFTER kill
  (LEAK if true): True` —— 孫プロセスは生き残った(手動で後片付け)。
  親は確かに消えた(`parent alive AFTER kill: False`)。これは上記の
  コード読解による予測を実機で裏付けるもので、「今は Job Object という
  選択肢自体が無く、`child.kill()` では孫が実際に漏れる」ことを
  推測ではなく再現された事実にしている。
- **当初の結論(2026-11-03)**: 項目3 は「未検証」ではなく「前提が崩れて
  いる」。永続コンテキストの本実装は (a) T4.4 の完了を前提にする、
  または (b) ラッパー自身が子孫 PID を自己追跡する、のいずれかを選ぶ
  必要があり、(a) を既定方針とした。
- **【結論変更】Opus レビューで判明(2026-11-04)**: (a) を本実装の
  前提にするのは、同じ「Windows では子孫を倒せない」制約を抱えたまま
  T5.1(timeout)・T6.2(`--detach`/`kill`)が既に出荷されていることと
  不整合。さらに Job Object は pywinauto の対象アプリ(既に起動済みの
  アプリ、COM 経由で別ホストから起動されるプロセス等、ラッパーの子孫
  でない場合が多い)に対して必要条件でも十分条件でもなく、
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を使えば操作対象として残したい
  アプリまで落ちる副作用もある。したがって T4.4 を待っても「終了処理
  が正しくなる」とは言えない。方針を「直接の子 kill で出荷し、孫
  プロセスの残存は T5.1/T6.2 と同じ既知の制約として明記する」に変更
  した(T4.4 完了時に自動的に改善される)。詳細は ADR-0013 §3
  (改訂3)参照。

## 項目4: `Concurrency::Reject` と永続コンテキストの相互排他の実装場所

- Date: 2026-11-03
- 調査方法: コード読解(`src/jobs.rs:176-220`)。実行は伴わない。
- `Concurrency::Reject` は `JobRegistry::start`(`src/jobs.rs:176`)の中で、
  **`JobRegistry` 自身が保持する `jobs: HashMap` を `job.target == target`
  で線形走査する**ことで実装されている。ロックも `JobRegistry` 内部の
  `Mutex` 止まりで、他のレジストリの状態は一切見えない。
- ADR-0013 は `PersistentContextRegistry` を `JobRegistry` とは独立した
  別レジストリにすると明記している(`Runner::spawn` の `Stdio::null()`
  前提と非終端プロセスの扱いが競合するため)。この設計のままだと、
  **通常の `exec`(`JobRegistry::start` 経由)と永続コンテキストの起動/
  ターンは、互いの存在を一切知らない 2 つの独立したロック・マップの下で
  並走できてしまう**。`Concurrency::Reject` を両者のどちらの内部に実装
  しても、もう一方からは見えない。
- **実装場所の当初案(2026-11-03 時点)**: どちらのレジストリにも実装を
  押し込まず、両方を呼び出す前段(`src/server/exec.rs` の exec
  ディスパッチハンドラ)に、ターゲット名をキーにした共有の「使用中」
  集合(`Arc<Mutex<HashSet<String>>>`)を新設する案。
- **【撤回】Opus レビューで欠陥が判明(2026-11-04)**: この案は
  `JobRegistry::open` が起動時に復元する `Orphaned`(再起動前に生きて
  いた子)の状態が見えず、サーバ再起動直後に通常 `exec` 側は弾かれる
  のに永続コンテキスト側は素通りする非対称が生じる。また `finish`/
  `kill`/`Lost` 遷移・detach・panic など `JobRegistry` のライフサイクル
  全経路に解放フックを重複して持つ必要があり、片方だけ更新されると
  集合がリークしたまま 409 を返し続けるか相互排他そのものが壊れる、
  という二重管理の問題を抱える。代わりに、永続コンテキストが
  `JobRegistry::start` で通常の job と同じ「席」を取る方式に変更した
  (前提として `persistent: true` ターゲットの単発 `exec` を禁止する)。
  詳細は ADR-0013 §3(改訂3)参照。

## 項目5: 毎ターンのハッシュ再検証コスト

- Date: 2026-11-03(デバッグビルド)、2026-11-04(release ビルドで再測定。
  改訂3。Opus レビューで「デバッグビルドの数字は本番の値ではない」と
  指摘された)
- Command: `cargo test --bin clipwire store::tests::poc_t9_3_item5 --
  -- --ignored --nocapture`(デバッグ)/ `cargo test --release --bin
  clipwire store::tests::poc_t9_3_item5 -- --ignored --nocapture`
  (release)
- 実機相当の件数(dragonflyg4 の `registered.toml` は 1571 件、T9.0
  evidence 参照)で、既存の再検証経路そのもの(`Store::verified_target`
  → `load_target_map` → `verify_approval`)を 20 回呼んで平均コストを
  測定。
- **実測**(`registered.toml`、220,863 バイト、1571 エントリ):
  - デバッグビルド(`opt-level=0`): `verified_target` 1 回あたり平均
    **約 317ms**。内訳: `fs::read_to_string` = 131〜134µs、
    `toml::from_str` = 288〜356ms、`fs::metadata(...).modified()` =
    26〜39µs。
  - **release ビルド(`opt-level=3, lto=true`。本番と同じプロファイル)**:
    `verified_target` 1 回あたり平均 **約 19.2ms**(20 回平均、合計
    383.6ms)。内訳: `fs::read_to_string` = 229µs、`toml::from_str` =
    **11.4ms**、`fs::metadata(...).modified()` = 19µs。
  - デバッグ比で **約 16.5 倍速い**。支配的コストは release でも変わらず
    `toml::from_str` だが、絶対値は「明確に対話性を損なう 300ms」から
    「十数 ms」に下がる。
- **結論(改訂3で変更)**: release ビルドでの実測(約 19ms)は、PoC 時点
  で想定していた「応答性を明確に損なう 300ms」ほど深刻ではない。mtime
  ゲート(`registered.toml` の再パースを、変化がなければ省略する仕組み)
  は、**「必須の設計変更」ではなく「対話的応答性のための任意の最適化」**
  に位置づけを下げる(ADR-0013 改訂3)。ただし 19ms はターンごとに
  積み重なるコストであり、ゲート自体に害はなく実装コストも小さいため、
  採用はそのまま推奨する。
- **ゲートの正しさに関する追加の指摘(Opus レビュー、改訂3で反映)**:
  当初の設計(mtime が変わっていなければ (a) `registered.toml` の
  再パースと (b) `approved/<hash>.json` の検証の両方を省略する)は、
  `approved/<hash>.json` の削除・改ざん・部分書き込み(ADR-0010 §3 が
  「改ざん・部分書き込みの検出」と位置づける検査)を検知できなくする
  退化を招く。(b) は数 KB の読み込み + sha256 で µs〜数十 µs にすぎず
  支配的コストではないため、**ゲートの対象は (a) のみに限定し、(b) は
  mtime に関わらず毎ターン必ず行う**ように ADR-0013 §3 を修正した。
  また mtime 単独ではなく `(ファイル identity, size, mtime)` の組を
  `!=` で比較すること、mtime はロック内・パース前に取得することも
  ADR に明記した(詳細は ADR-0013 §3 参照)。
- **付随して判明した既存コードの観察(本 PoC の対象外。別途記録する
  価値がある)**: 通常の単発 `exec` も `prepare()`(`src/server/exec.rs`)
  経由で毎回 `verified_target` を呼んでおり、この実測コスト(release
  でも約 19ms、デバッグでは約 300ms)を既に払っている。`prepare` は
  同期関数として async ハンドラから直接呼ばれており(`spawn_blocking`
  されていない)、呼び出しのたびに tokio ワーカースレッドをその時間
  ブロックする。永続コンテキスト固有の問題ではなく、既存の `exec`
  経路全体に関わる観察。

## 付記: ベンチマークテストの CI 安定性

`store::tests::poc_t9_3_item5_verified_target_cost_against_1571_entries`
は 20 回 x 約 300ms の CPU 束縛な `toml::from_str` を連続実行するため、
デフォルトの `cargo test` 並列実行下で他のタイミング依存テスト
(`ac_t6_1_5_*`・`ac_t4_5_6_*` 等)を不安定化させることが、push 後の
CI(run 41751250415、`linux` ジョブのみ失敗)と、ローカルでの複数回
再現で確認された。`#[ignore]` を付けて通常の `cargo test`/CI から外し、
`cargo test -- --ignored` での単独実行専用にした(測定結果そのものは
変わらない。不安定化の原因が測定対象ではなく並列実行の資源競合である
ことをローカルで確認済み)。

## 全体のまとめ(AC-T9.3.2 への入力。改訂3で更新)

- 項目1・2: 設計方針どおりに動くことを実プロセス・実機・Windows CI で
  確認した(項目1は出力順序の保証がないという制約つき。プロトコル
  応答を fd 1 から分離する設計でフレーミング破壊のリスクも塞いだ)。
- 項目3: Windows Job Object 統合(T4.4)がまだ実装されていないことが
  判明したが、Opus レビューで「これを理由に本実装を止めるのは T5.1/
  T6.2 の扱いと不整合」「Job Object は pywinauto の対象アプリに
  必要条件でも十分条件でもない」と指摘され、T4.4 待ちにしない方針へ
  改訂した(ADR-0013 §3)。
- 項目4: 当初案(exec ディスパッチ層への共有集合)は `JobRegistry` の
  `Orphaned` 復元状態が見えない・解放経路が二重管理になるという欠陥が
  Opus レビューで判明し、永続コンテキストが `JobRegistry::start` で
  「席」を取る方式に改訂した。前提として `persistent: true` ターゲット
  の単発 `exec` を禁止する。
- 項目5: デバッグビルドでの実測(約 300ms)は release ビルドでは
  約 19ms に下がり、mtime ゲートは「必須」から「任意の最適化」に
  格下げされた。ゲートの対象を `registered.toml` の再パースのみに
  限定し、`approved/<hash>.json` 側は毎ターン必ず検証する(Opus
  レビューで、ゲートが承認完全性検査を弱めてしまう欠陥を指摘された)。
- 結論として、PoC(T9.3)自体は完了したが、改訂2の Decision には
  Opus レビューで複数の実質的な欠陥が見つかったため、ADR-0013 改訂3
  で Decision を再修正した。本実装着手前の残りの未決事項は ADR-0013
  の「Status」節を参照。
