# ADR-0006: 承認フローの強化(縮小版)

- Status: Proposed (改訂2: Opus 再レビュー反映。TTL・静的警告・差分要約 toast は見送り)
- Date: 2026-09-30
- Depends on: ADR-0010(ハッシュ/承認レコード/原子ストア/承認の経路), ADR-0011(toast のエスケープ), ADR-0003(監査)

## Context

承認された script は任意コードであり、最大のリスク面。Opus レビューで次が指摘された。

- toast に名前と差分要約しか出さず、「承認」で即 registered に入る導線は、構造的に**盲目承認**になる(再 register で script の中ほどに 1 行追加されても「+1/-0 行」と出るだけ)。ADR が「境界は人間の全文確認」と言いながら、既定導線で全文を見ない。
- 承認がハッシュに束縛されていない。`show` で内容 A を確認した後に、同名で内容 B が再 register され、`approve` すると B が承認される。toast 側も、toast1(A)の承認が A を登録し、B の pending を黙って消す。
- 現行コードは Dismissed で待機を終える。Dismissed は数秒で画面から消えた(アクションセンターへ移った)時点でも発火するため、実際に押せるのは数秒間のみ。
- 同一内容の再 register でも承認を取り消して再承認を求める(承認疲れ)。
- 拒否・無視で `pending.toml` に残り続ける。
- `register` 時の案内文が実態(toast が主導線)とずれている。

> **適用範囲**: 本 ADR は**手動承認モード**(`--auto-approve` なしで起動したサーバ)の承認フローを定める。実運用は自動承認(`--auto-approve`)で、そのモードでは `register` が承認を兼ね、本 ADR の承認 UI(2 段階 toast・レビュー画面)は使われない。自動承認でも適用されるのは、同一ハッシュの no-op 再登録・承認レコードの記録・監査(0010/0003)である。実装は手動承認モードを使う判断をした時点まで後回し(docs/tasks の Phase 5b)。

> **脅威モデル**: README の「脅威モデル」節を参照。この承認フローは、誤操作・意図しないコマンド・tailnet 上の第三者・ブラウザ経由の攻撃を防ぐ。悪意ある(乗っ取られた)Linux 側は防がない。リポジトリのコードをビルドするターゲットの承認は、そのリポジトリへの書き込み権を持つ者に Windows ユーザー権限を渡すことと同じである。

## Decision

1. **承認は常に `(name, hash)` の組で行う**(ADR-0010)。
   - toast のボタン引数は `approve:<full-hash>` / `deny:<full-hash>`。承認時に pending の現行ハッシュと一致しなければ拒否し、何もしない(pending は消さない)。
   - CLI は `clipwire approve <name> --hash <prefix>` を必須にする(表示済みのハッシュと合わせる)。
   - 書き込み直前にハッシュを再確認する。
2. **toast は「内容を見る」「拒否」の 2 ボタン**にする。
   - 「内容を見る」: clipwire が**整形した**レビューファイルを `%LOCALAPPDATA%\clipwire\review\<hash>.txt`(読み取り専用属性)に書き出し、メモ帳で開く。続けて、同じハッシュに束縛された「承認」「拒否」の 2 ボタンの toast(`scenario="reminder"`)を出す。
   - **レビューファイルの形式**(目視が唯一の境界なので、中身を隠せないようにする):
     - 冒頭に、ハッシュ全体・dir・env・timeout・concurrency・params と、警告サマリ(「非 ASCII 文字 n 個 / 最長行 m 桁」)を出す。
     - 全文(行番号付き、各行を 120 桁で強制折り返し)と、再承認時は承認済み版(`approved/<hash>.json`)との unified diff の**両方**を載せる(diff だけでは既存の関数・変数の再定義を見落とすため)。
     - **見えない文字・紛らわしい文字だけ** `\u{XXXX}` 表記に置き換える: Cc、Cf、Zl、Zp、ASCII のスペース以外の Zs、Mn / Me(結合文字・異体字セレクタ)、Hangul Filler(U+115F, U+1160, U+3164)、U+2800。CJK・かな・全角記号はそのまま表示する(日本語が読めなくなって読み飛ばされるのを避ける)。非 ASCII を含む行は行頭にマーカーを付け、警告サマリに「文字体系が混在する識別子(ラテン文字とキリル文字など)」を出す。
     - メモ帳の起動は `start_detached` 相当(標準ハンドルなし、Job の外)で行う。レビューファイルは承認・拒否・掃除の時点で削除する(`review\` に溜めない)。
     - register 時の制御文字・双方向制御文字の拒否は ADR-0010 §1 が持つ(二重の防御)。
   - 新規(初回)登録も同じ導線とする(初回こそ全文を見る価値が高い)。
   - 即承認を残す例外は設けない(TTL 失効後の再承認という例外は、TTL を見送るため不要)。
3. **toast の寿命**: `scenario="reminder"`(操作するまで画面に残る)を付ける。Dismissed の reason が `TimedOut`(画面から退いただけ)の場合は待機を続ける。待機の上限は pending の保持期限に合わせる(`pending_ttl` 24h。超過分は次回の register 時とサーバ起動時に掃除)。ユーザーが×で閉じた場合(reason=`UserCanceled`)は「無視」とする(拒否ではない)。待機スレッドは**ハッシュごとに 1 本**にし、pending が溜まってもスレッドが溜まらないようにする。サーバ起動時に `ToastNotificationManager::History().Clear(AUMID)` で古い toast を消し、未処理の pending について toast を出し直す。
4. **拒否**: pending から削除し、監査ログに `deny` を記録する。無視は pending に残す(上の期限で掃除)。
5. **同一ハッシュの再 register は no-op**(ADR-0010 §5)。再承認を要求しない。
6. **Windows 側 CLI**: `clipwire pending`(一覧)、`clipwire show <name>`(全文 + diff)、`clipwire approve <name> --hash <prefix>` / `clipwire deny <name>`(toast が使えない状況のフォールバック。`approve` は `show` 相当を表示して `y/N`、`--yes` で省略)。これらは **HTTP を使わず**、Windows 側でローカルに、ADR-0010 §4 のミューテックスを取りファイルを直接読み書きする(サーバの稼働は不要)。トークンを持つリモートクライアントからは、承認・拒否を行う手段が存在しない。`deny <name>` も、表示と確認を同一プロセスで行うか、`--hash <prefix>` を指定できる(表示したものと違う再 register を誤って消さないため)。
7. **メッセージ整理**: `register` の応答と `409` は「Windows の通知で内容を確認して承認してください(通知が出ない場合: `clipwire approve <name> --hash ...`)」に統一する。
8. 承認・拒否・失効の操作はすべて監査ログへ(ADR-0003)。

### 見送り(Deferred)

- **TTL / 「1 時間だけ承認」**: 承認疲れを増やし、盲目承認を助長するため見送り。必要になれば別 ADR。
- **静的警告**(`cmd /c` に `args` を渡している等): 誤検知・見逃しがあり、安心材料として誤用されうるため見送り。
- **差分要約 toast**: 要約は承認判断の根拠として不十分であり、上記 2 の全文確認に置き換える。

## Consequences

- 承認者が実際に全文(または diff)を見てから承認する導線になる。ハッシュ束縛により TOCTOU が無くなる。
- 承認の手間が増える(常に「内容を見る」を経由)。**手動承認モードでは**、承認頻度(再 register 時のみ)が低い前提で許容できると判断した。ただし、実運用は自動承認で使い捨てターゲット(1571 件規模)を大量に作るため、この前提は手動承認モードに**移行する場合には成り立たない**(移行するなら、使い捨て実行の代替設計が要る)。同一内容の再 register が no-op になることで、頻度は下げる。
- toast 周りの実装(2 段階 toast、メモ帳起動、`scenario="reminder"`、Dismissed の扱い)が増える。
- 承認がローカルのファイル操作に限られるため、トークン保持者(Linux 側)が自分で承認する経路がない。なお、Windows 上でユーザー権限で動く**承認済みスクリプト**は、承認ファイルを書き換えることも元々可能である。これは権限の上昇ではなく、この設計の前提として受け入れる。
- **PoC で確認する項目**: (1) 非パッケージアプリで COM activator 未登録の場合、アクションセンターからボタンを押したとき in-process の `Activated` が発火するか。(2) サーバ再起動後に、前プロセスが出した toast のボタンを押すとどうなるか(ショートカットの AUMID 経由で引数なしの clipwire が起動しないか)。(3) 集中モード中の `scenario="reminder"` の扱い。

## Alternatives considered

- **toast で即承認 + 差分要約**: 盲目承認になるため却下。
- **ターゲットの署名方式**: 鍵管理が増え、サーバ側の人間承認という現行の強みを失う。
