# ADR-0012: Windows へのファイル送信と、サーバの自己紹介(発見性)

- Status: Proposed
- Date: 2026-11-27
- 依存: 0011(HTTP 面の信頼境界)、0010(ストア・承認は HTTP に載せない)、0003(監査ログ)

## Context

2026-11-27、別セッションのエージェントが Windows の Downloads に PPTX(約 98 KB)を置こうとしたが、clipwire にはアップロード経路がなかった(`GET /file` は読み取り専用)。回避策として exec ターゲット `save-clip-file-to-downloads` を登録した。これは、クリップボードに `CLIPWIRE-FILE:<b64 名前>:<b64 本体>` を `POST /clip` で載せてから、PowerShell で Downloads に書き出す。成功はしたが、問題が 3 つある。

1. **ユーザーのクリップボードが上書きされる**。また、base64 で文字列として載せるため、大きいファイルには向かない。
2. **ファイル名の検証がない**。自動承認運用では、ターゲットのスクリプトに入れた検証しか効かない。`..\..\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\x.cmd` のような名前を渡せば、ログオン時にコードを実行させられる。
3. 同じ要求のたびに、使い捨てのターゲットが増える(実運用は 1571 件すべて script 形式で、大半が使い捨て)。

同じ作業の中で、エージェントは 19999 番ポートが何のサーバか分からず、SSH や SOCKS を試した。サーバには「自分が何か、何ができるか」を答える口がない(`/health` は `OK` か `version` だけを返す)。存在しないパスには空の 404 が返る。登録したターゲットを消す手段もない。

## Decision

### 1. `POST /files`(ファイル受信)

- **本文は生バイト**で、`Content-Type: application/octet-stream` を必須とする(それ以外は 415)。ファイル名はクエリ `?name=<パーセントエンコードした UTF-8>` で渡す。ヘッダで渡さないのは、HTTP ヘッダに非 ASCII を載せる方法が標準化されていないため。
- **保存先は 1 か所に固定**する。既定は Windows の Downloads(Known Folder `FOLDERID_Downloads`。取れなければ `%USERPROFILE%\Downloads`)。`serve --files-dir <path>` で変更できる。リクエストからは保存先を指定できない(サブディレクトリも不可)。存在しない保存先は作らず、500 を返す。
- **ファイル名の検証**(純粋関数。違反は 400。理由を本文に書く):
  - 空、または 200 文字を超えるもの。
  - 制御文字(C0、DEL、C1)、および Windows でパスに使えない `\ / : * ? " < > |`。
  - 先頭の `.`、`..` を含むもの、先頭の空白、末尾の `.` と空白(Windows は末尾の `.`・空白を黙って落とすため、名前の同一性が崩れる)。
  - 予約デバイス名(`CON` `PRN` `AUX` `NUL` `COM0-9` `LPT0-9` と、上付き数字の `COM¹` など。拡張子つき `CON.txt` も)。
  - 双方向テキストの制御文字(U+200E/F、U+202A〜202E、U+2066〜2069)。`invoice‮fdp.exe` のような拡張子の偽装を防ぐ。
  - **Explorer がフォルダを表示するだけで解釈する種類**: 拡張子 `.lnk` `.url` `.scf` `.library-ms` `.searchconnector-ms`、および名前 `desktop.ini`。これらは開かなくても、表示時にアイコン取得などで外部への接続(NTLM 認証の送出を含む)が起きうる。
- **同名ファイルがあれば** `name (1).ext`、`name (2).ext` … とする(最後の `.` の前に入れる)。`(999)` まで埋まっていれば 409。存在確認と作成は `create_new` で 1 操作にし、競合しても上書きしない。
- **サイズの上限**は既定 100 MiB で、`serve --files-max-bytes <n>` で変える。`Content-Length` が上限を超えていれば読まずに 413。本文は**ストリームでファイルへ書き**、途中で上限を超えたら、書きかけのファイルを消して 413 を返す。転送が切れた場合も消す。
- **Mark of the Web**: Windows では、保存したファイルに `Zone.Identifier`(`ZoneId=3`)の代替データストリームを付ける。インターネット由来のファイルを Linux 側のエージェントが中継しても、SmartScreen と Office の保護ビューが効くようにする(エージェントの誤操作は脅威モデルの守る対象)。`serve --files-no-motw` で付けない。ADS を書けないファイルシステム(FAT 等)では警告だけ出して続ける。
- **通知と監査**: 保存したら toast(`ファイルを受信しました: <名前> (<サイズ>)`。WinRT 経路、XML エスケープ済み。0011 §A-2/3)を出し、監査ログに `file-receive` イベント(保存した名前、バイト数、sha256、接続元 IP、`clip` の有無)を記録する。
- **`?clip=1`**: 保存したファイルを `CF_HDROP`(+ `Preferred DropEffect` = コピー)でクリップボードに載せ、Explorer で貼り付けられるようにする。載せるパスは**今回保存したファイルだけ**(`POST /clip` から任意のパスの `CF_HDROP` は作れない)。クリップボードへの書き込みに失敗しても、保存は成功として扱い、応答に `clip_error` を入れる。
- **応答**: 201 と JSON `{"name", "path", "bytes", "sha256", "clipboard"}`(`clip_error` は失敗時のみ)。

### 2. 信頼境界(0011 との整合)

- `/files` は**保護ルート**と同じ認証を使う(トークン必須。トークン未設定で `--allow-no-token` があれば認証なし、なければ 403)。クリップボード系(`/clip` 等)より一段強い。ファイルの書き込みは、クリップボードと違って永続し、ユーザーが後で開くため。
- Origin の拒否・Host の許可リストは全ルート共通で適用する(0011 §7・§8)。`Content-Type: application/octet-stream` は CORS の単純リクエストに使えない型なので、ブラウザからはプリフライトなしに送れない。0011 §9 の「POST は JSON」の例外は、この理由で `/files` だけに認める。
- **自動承認モード**では、トークン = Windows ユーザー権限でのコード実行なので、`/files` で新たに渡す権限はない(exec で同じことができる)。むしろ、使い捨てターゲットを経由するより、ファイル名の検証・保存先の固定・監査が効く分だけ安全になる。
- **手動承認モード**では、`/files` はトークン保有者に「Downloads に任意の内容のファイルを置く」権限を新たに渡す。置くだけでは実行されない(保存先が固定でスタートアップ等に置けない、Explorer が表示時に解釈する種類は拒否、MotW が付く)。ユーザーが自分で開けば実行されうるが、これはブラウザでのダウンロードと同じ水準とみなす。
- 脅威モデルの「守らない対象」(Linux 側そのものの悪意)は変えない。上の検証は「誤操作」と「ネットワーク越しの第三者」への境界である。

### 3. `GET /info`(自己紹介)

- **認証なし**(`/health` と同じ共通ルート)。`{"app": "clipwire", "version", "features": [...], "endpoints": [{"method", "path", "auth", "summary"}], "files": {"max_bytes"}}` を返す。
- `features` は機能名の固定リスト(`clip`, `clip-png`, `clip-svg`, `files`, `files-clip`, `exec`, `exec-stream`, `jobs`, `targets`, `unregister` など)。互換ネゴシエーション(2026-10-01 に削除)の復活ではなく、**人間とエージェントが読むための説明**である。クライアントはこれを見て送信を拒否したりしない。
- 保存先のパス(ユーザー名を含む)やトークンの有無は返さない。
- エンドポイント一覧は、ルーティング表(`ROUTES`)から作る。表と説明がずれないようにするため。

### 4. `GET /targets`(登録済みの一覧)

- **保護ルート**。registered と pending の名前・状態・ハッシュ・承認時刻を返す。**定義の本文は返さない**(`/targets/check` と同じ方針。本文はトークンを含みうる)。

### 5. `DELETE /register/:name`(登録の削除)

- **保護ルート**。registered と pending の両方から、その名前を消す。どちらにもなければ 404。消したら監査ログに `unregister`(名前、ハッシュ、接続元 IP)を記録する。
- **手動承認モードでも許す**。0010 §4 が HTTP に載せないのは「承認(権限を与える操作)」で、削除は権限を減らす操作だから。削除後に同じ名前を `register` すれば、手動承認モードでは承認待ちに戻る。
- 承認レコード(`approved/`)は内容アドレス方式なので消さない(90 日の掃除に任せる)。実行中のジョブは止めない(止めるのは `kill`)。
- パスを `/targets/:name` にしないのは、既存の `POST /targets/check` と、`check` という名前のターゲットの削除がぶつかるため。

### 6. 存在しないパス(404)

- 空の 404 ではなく、本文にエンドポイント一覧(3 と同じ表から作る)と `GET /info` の案内を返す(`text/plain`)。Origin・Host の検査は、ほかのルートと同じく先に効く。

### 7. クライアント

- `clipwire send FILE [--name NAME] [--clip]`: ファイルを `POST /files` へストリームで送り、保存先のパスを表示する。
- `clipwire unregister NAME`: `DELETE /register/NAME`。
- `clipwire info`: `GET /info` を表示する。

## Consequences

- 使い捨てのファイル書き出しターゲットが要らなくなり、クリップボードを汚さずに送れる。`save-clip-file-to-downloads` は、この ADR の実装を出荷したあと `clipwire unregister` で消す。
- 手動承認モードでは、トークンで渡す権限が「Downloads への書き込み」の分だけ増える(§2)。
- 一覧・削除・自己紹介ができるようになり、エージェントが手探りで別のプロトコルを試す必要がなくなる。
- 0011 §9(POST は JSON 必須)に、`/files` という例外が 1 つ増える。例外はルーティング表のクラス(`Upload`)で表し、テストで固定する。

## Alternatives considered

- **`POST /clip` の拡張で CF_HDROP を受ける**: クリップボードを経由する限り、ユーザーのクリップボードを上書きする問題が残る。
- **保存先をリクエストで指定できるようにする**: 許可リストを作っても、スタートアップフォルダ等への書き込みを確実に防ぐのが難しい。必要になれば、設定で名前つきの保存先(`downloads` など)を複数定義し、名前だけを指定させる。今回は Downloads だけで足りる。
- **multipart/form-data**: ブラウザの単純リクエストで送れてしまう型であり、ファイル 1 個には過剰。
- **書きかけを一時ファイルに書いて rename する**: Windows の `rename` は既存ファイルを置き換えるため、競合時に上書きしない保証が `create_new` より弱くなる。書きかけが短時間見えることは許容する(失敗時は消す)。
