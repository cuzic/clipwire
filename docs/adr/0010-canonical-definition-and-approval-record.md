# ADR-0010: 定義の正規形・ハッシュ・承認レコード・プロトコル版

- Status: Proposed (改訂2: Opus 再レビュー反映)
- Date: 2026-09-30
- Depends on: なし
- Used by: ADR-0004, 0005, 0006, 0003(監査)

## Context

Opus レビューで次が指摘された。

- `StoredTarget.env` が `HashMap` のためハッシュが非決定的になる。
- Linux と Windows が独立にハッシュを計算する方式は、バージョン不一致で一致しない。
- `clipwire approve --dir` は承認時に dir を書き換え、クライアント定義とハッシュが永久に一致しなくなる。
- 新フィールドは旧サーバに黙って捨てられる。
- `pending.toml` / `registered.toml` はロックなし・非原子的に書かれ、破損すると次の書き込みで**全承認が消える**。
- 承認操作がハッシュに束縛されていない。
- 監査ログにハッシュを記録しても本文が残らない。
- **承認を HTTP API 化すると、トークン(Linux 側のクライアントも保持)だけで `register` → `approve` が完結し、人間の承認が不要になる(再レビュー Critical)。Host ヘッダは接続元の証明にならず、同じ Router が Tailscale リスナーにも載る。**

## Decision

### 1. 正規形とハッシュ

- 正規形: `{"v":1, "dir":..., "script"|"steps":..., "env":{…}, ...}`。`env` は `BTreeMap`(ソート済み)。
- **未設定のフィールドはシリアライズしない**。サーバは既定値(例: `timeout` の 30m)を補完して保存・ハッシュ計算しない。既定値はハッシュ計算後に実行時に適用する。既存の承認は失効しない。
- ハッシュ = `sha256(正規 JSON のバイト列)`。**ハッシュはサーバだけが計算する**。`register` の応答に返す。`POST /targets/check`(ADR-0005)は、クライアントの定義をサーバに投げて registered と比較させる(本文は返さない)。
- `clipwire approve --dir` は廃止する。
- `BTreeMap` 化は**最初のリリースに含める**(ハッシュの保存・表示より前)。
- **定義の検証(register 時)**: `script` / `steps` / `env` / `dir` に、Unicode の制御文字・書式文字(カテゴリ Cc, Cf。ただし TAB・LF・CRLF を除く)を含むものは `400`。双方向制御文字(U+202A–202E, U+2066–2069)・ゼロ幅文字・NUL・単独の CR を含むためである。対象は **Cc、Cf、Zl、Zp(U+2028/2029)、および Hangul Filler(U+115F, U+1160, U+3164)** とする。文字列リテラル中の日本語など通常の非 ASCII は許可する。ZWJ を使う合成絵文字・BOM・ソフトハイフンも Cf なので拒否されるが、個人用途の頻度としては許容する。**400 の応答には、位置(行・桁)とコードポイントを含める**。`name` の検証は ADR-0011 が持つ。

### 2. リクエスト形式とプロトコル版

- `register` のリクエストを `{"name": "...", "target": { ... }}` の入れ子にし、`#[serde(deny_unknown_fields)]` を付ける。
- **旧フラット形式**(`{name, dir, script, steps, env}`)は、`serde(flatten)` と `deny_unknown_fields` が併用できないため、`flatten` を使わず、列挙フィールドを持つ**専用の struct** に `deny_unknown_fields` を付けて受ける。デシリアライズは、入れ子形式を先に試し、失敗したら旧形式を試す。旧形式の受理は `proto=2` の間のみとし、`proto=3` で打ち切る。
- `GET /health` は `{"version":"...","proto":N,"features":["stream","jobs","params",...]}` を返す(既存の `OK\n` を期待する利用者向けに、`Accept: application/json` のときのみ JSON)。
- クライアントは `register` / `exec` の前に features を確認し、**サーバが未対応のフィールドを含む定義は送信前にエラー**にする。`exec` の `args` も同様。
- この機構は、`timeout` / `concurrency` / `params` を導入する ADR-0003/0002/0004 より**先**に入れる。

### 3. 承認レコード

- 承認時、承認された**正規 JSON のバイト列そのもの**を `%APPDATA%\clipwire\approved\<sha256>.json` として保存する(TOML に戻して再生成するとバイト列が変わりうるため)。監査ログのハッシュから本文を復元でき、ADR-0006 の差分表示とロールバックにも使える。
- `registered.toml` のエントリは、**本文(dir/script/steps/env)を残したまま `hash` と `approved_at` を追加する**(追加だけの移行)。旧サーバ(P3 より前のバイナリ。ウォッチドッグによる自動フォールバックで起動しうる)は余分なフィールドを無視して従来どおり動き、移行済みのストアを壊さない。本文の削除は、旧版へ戻す可能性がなくなった後に別途行う。
- **exec 時に、`approved/<hash>.json` を読み、sha256 を再計算してハッシュと一致しなければ実行を拒否する**(改ざん・部分書き込みの検出)。あわせて、エントリの本文が同じ `hash` に正規化されることを検証し、不一致なら拒否する。
- **移行**: 既存の `registered.toml`(本文を持つエントリ)は、サーバ起動時に、ストアのロック(§4)を取って `approved/` を生成し、エントリに `hash`/`approved_at` を追加する(冪等。旧サーバが書き戻して `hash` が消えても、次の起動で復元される)。読み込み経路では書き込まない。`approve --dir` で dir を書き換えていた既存エントリは、移行後の `list` で `changed` になるため、再 register が必要(リリースノートに記載)。

### 4. ストアの原子性と承認の経路

- `pending.toml` / `registered.toml` / `approved/*` の書き込みは、一時ファイルに書いて `rename` する原子書き込みにする。
- **書き込みはすべて、サーバと CLI が共有する名前付きミューテックス `Global\clipwire_store` を取って行う**(サーバ内の直列化は加えて `tokio::sync::Mutex`)。
- **承認系(`approve` / `deny` / `pending` / `show`)は HTTP に載せない**。`clipwire approve` / `deny` は、Windows 側でローカルに、ミューテックスを取り**ファイルを直接読み書きする**。サーバの稼働は不要。承認は、ローカル(Windows セッション内)で人間が操作する経路だけに限る。トークンを持つリモートクライアントからは、承認を行う手段が存在しない。
  - 理由: トークンは Linux 側のクライアント(ターゲットを書く側)も持つため、トークンだけで認可される承認 API があれば、`register` の直後に自分で承認できる。Host / Origin の検査は DNS rebinding・CSRF 対策であって認可には使えない(ADR-0011)。承認を別の loopback 専用リスナー+管理用シークレットで認可する案もあるが、攻撃面が増えるため採用しない。
  - 前提: Windows 側でユーザー権限で動く承認済みスクリプトは、元々任意のことができるため、承認ファイルを書き換えることも可能。これは権限の上昇ではない(ADR-0006 に明記)。
- **ミューテックスの注意点**:
  - 名前は `Global\clipwire_store` にする(SSH 等の別ログオンセッションからも排他するため。単一起動のミューテックスは既に `Global\`)。
  - Windows のミューテックスはスレッドに所属する。tokio の async 関数で取得して `.await` を挟むと `ReleaseMutex` が `ERROR_NOT_OWNER` で失敗するため、「取得 → 読む → 変更 → 原子書き込み → 解放」は 1 つの `spawn_blocking`(await なし)か専用スレッドの中で完結させる。
  - CLI の `approve` の `y/N` 確認は**ロックの外**で行い、書き込む直前にロックの中でハッシュを再確認する(確認中にサーバの register や toast を止めない)。
  - 取得にはタイムアウトを付ける。`WAIT_ABANDONED` のときは、ファイルを parse して検証してから続行する。
  - サーバと CLI は**同じ権限**(同じ整合性レベル)で動かす。ミューテックスを開けない場合は、ロックなしで続行せずエラーにする。
- 読み込み(parse)に失敗したファイルは**空扱いにして上書きしない**。`*.corrupt.<時刻>` へ退避し、書き込みを拒否してエラーを出す。直前の正常版を `.bak` に世代 1 で残す。

### 4b. 自動承認モード(`--auto-approve`)

- 自動承認では `register` が承認を兼ねる。この場合も、**§3 の承認レコード(`approved/<hash>.json`)を書き、`registered.toml` のエントリを `{hash, approved_at}` で作る**(書かないと、`exec` 時のハッシュ再検証で全ターゲットが拒否される)。承認者は `auto` として監査(ADR-0003)に記録する。同一内容の再 register は §5 のとおり冪等(`approved/` のファイルが増えない)。
- 使い捨てターゲットが多いため `approved/` が増え続ける。掃除は docs/tasks T5.7(registered に参照されず、監査の保持期間を過ぎたものを削除)。

### 5. 同一内容の再登録

- `register` された定義のハッシュが、registered と同一なら **no-op**(再承認を求めない)。さらに、別ハッシュの pending が残っていれば、それは掃除する(元の内容に戻したことが明らかなため)。
- pending に同一ハッシュがあるときは、toast の待機スレッドが生きていなければ、toast を再表示する(ADR-0006 §3。toast を失った場合の復帰手段)。待機スレッドが生きていれば再表示しない。

## Consequences

- ハッシュが決定的になり、`list` が信頼できる。サーバ計算方式で、Linux/Windows のバージョン不一致でも食い違わない。
- 旧サーバへ新フィールドを送って無効なまま承認される事故を、feature チェックで防げる。
- 承認レコードが残るため、監査・差分・ロールバックの土台ができる。exec 時のハッシュ再検証で、改ざんを検出できる。
- 承認がローカルのファイル操作に限られるため、トークンを持つリモートからは承認できない。サーバの稼働も不要。
- 名前付きミューテックスとファイルの直接操作により、CLI とサーバの競合を避けられる(ミューテックスは同一ログオンセッション内。サーバはユーザーセッションで動かす前提)。
- プロトコル版の管理コストが増える。

## Alternatives considered

- **承認を localhost の HTTP API にする(初版の本 ADR)**: トークンだけで承認でき、人間の承認が不要になるため却下(再レビュー Critical)。
- **loopback 専用リスナー + 別の管理用シークレット**: 攻撃面(別ポート、秘密ファイル)が増える。ファイル直接操作の方が単純で、攻撃面が小さい。
- **Linux/Windows が同一コードで独立にハッシュ計算**: バージョン不一致で一致しない。
- **SQLite でストア**: 依存と移行コストが増える。
