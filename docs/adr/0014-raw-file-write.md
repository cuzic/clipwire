# ADR-0014: 生ファイル書き込み (`/write`)

- Status: Proposed(実装計画に進める段階。Opus 3 回目レビューで N1〜N4 は解消。残りは §1(許可ルートの重複方向・バイナリ配置先の denylist 追加)・§6(字句チェックの実行順)・§10(無効時のステータスコード)のテキスト修正のみ)
- Date: 2026-11-03(ADR-0012 から分離)
- Depends on: ADR-0009(ランナー)、ADR-0010(正規形・ハッシュ・承認レコード)、ADR-0011(HTTP 面の信頼境界)
- See also: ADR-0012(`script_file`。当初は本機能と同じ ADR に同梱していたが、設計論点が多く分離した)

## Context

別プロジェクト(pad2py)が、clipwire を Windows VM 上の対話的 RDP セッションに届く唯一の経路として使っており、スクリプト本体を Windows 側に置くのに WinRM 側で base64 デコードする回り道が必要だった。`put`/`/clip` は Windows クリップボードへの書き込みのみで、任意のファイルパスへ直接書き込む手段が無い。

ファイルをディスクに書く処理自体に目新しさはないが、§6/§7 で述べるとおり、正規化(`canonicalize`/`GetFinalPathNameByHandleW`)と原子的な置き換え(`MoveFileExW`)には既存の `src/win.rs` には無い呼び出しが要る。問題の中心は「どのルートクラス・認可で許可するか」という HTTP 面の設計と、パスの安全な扱いである。

### 当初案の誤り(Opus レビューで判明)

当初案は「README の脅威モデル(トークン = Windows ユーザー権限でのコード実行権限)により、`/write` は新しい権限を何も追加しない」という前提で、`/clip` と同じ信頼レベル(`RouteClass::Clipboard`、ハンドラ内 `check_auth`)に `/write` を乗せていた。これは誤りだった。

- **その等式は `--auto-approve` 運用でしか成立しない**。手動承認運用では、トークン保持者は `register`(人間の承認が必要)と、既に承認済みのハッシュへの `exec` しかできない。`ExecRequest` は `name`/`timeout`/`detach` しか運ばず、コードそのものは運べない。ADR-0004 は、実行時に任意の引数・文字列を差し込めると承認が無意味になるという理由で、まさにこの種の「実行時の自由入力」を明確に却下している。
- `/write` がこの前提のまま `RouteClass::Clipboard` に乗ると、手動承認運用でも**人間の確認なしにコード実行と等価な操作**(スタートアップフォルダへの `.cmd` 配置、`$PROFILE`/`sitecustomize.py`/`.cargo/config.toml` への書き込み、承認済み `steps` が指す実行中スクリプトの差し替え、等)が可能になり、手動承認運用を実質的に自動承認運用へ格下げする。
- さらに、`RouteClass::Clipboard` の `check_auth` はトークン未設定時に `true` を返す。`--bind-localhost-only` のみ(トークンなし、`--allow-no-token` なし)という、ADR-0011 §5 が `/exec` のために明確に閉じた構成で、`/write` だけは**無認証の任意ファイル書き込み**として開いたままになる。
- `clipwire_config_dir()` への書き込みを拒むガードは、「事故防止」ではなく ADR-0010 §4(承認を HTTP に載せない)が守ろうとしている境界そのものである。

これらを踏まえ、`/write` を**既定で無効、明示的な opt-in と許可ルートの指定が必須**の機能として設計する。

### 2回目の指摘: 残っていた4つの矛盾・誤り

1. **手動承認運用への影響の主張が過大**: 許可ルート(`--write-root`)が承認済みターゲットの `dir` やその参照先と重なる場合、そのターゲットは実質的に自動承認運用相当になる。「手動承認運用の意味を壊さない」と無条件に言ってはいけない。
2. **正規化仕様の自己矛盾**: 「純粋関数にする」という指示と、「`/file` と同じ `canonicalize()` を使う」という指示が同時に書かれていた。`canonicalize()` は OS 呼び出し(シンボリックリンク・ジャンクション・8.3 名の解決)であり、純粋関数では行えない。どちらか一方だけでは、ジャンクション経由の迂回を見逃すか、Linux でテストできないかのどちらかになる。
3. **上書き防止の実装方法の誤り**: Windows の `std::fs::rename` は既存ファイルを置き換える(`MOVEFILE_REPLACE_EXISTING` 相当)。「既定は作成のみ、存在すれば 409」を `exists()` 確認 → `rename` で実装すると競合も起き、しかも実際には上書きしてしまう。
4. **ボディサイズ制限の誤り**: axum の `DefaultBodyLimit` は `Bytes`/`String`/`Json` のようなバッファ系エクストラクタにのみ効き、ストリームする `Body` には効かない。「64 MiB まで、ストリームで書く」は、このまま実装すると制限が存在しない。

本 ADR の決定は、これら 4 点を踏まえて書き直したものである。

## Decision

### 1. 既定で無効。`--enable-write` + 必須の `--write-root`(複数指定可)

- 新しい起動フラグ `--enable-write` を追加する。`/write` ルートは**常にマウントする**(存在しないルートとして 404 にはしない。無効時は §10 のとおり 403 で区別する。古いサーバ(本 ADR 未実装)は未知のルートとして 404 を返し、それも区別点になる)。
- `--enable-write` には**少なくとも 1 つの `--write-root <dir>`**(複数指定可)が必須。無ければ起動時エラー。
- **起動時に許可ルート同士・denylist 対象の健全性を検査する**。次の**denylist 対象ディレクトリ**のいずれかと、許可ルートが**祖先・同一パス・配下のいずれか(重なる方向を問わない)**である場合、起動時エラーで拒否する(「このルートは広すぎます」。比較は §6(b) と同じコンポーネント単位の正規化比較を使う):
  - ドライブルート(`C:\` 等)。
  - `%USERPROFILE%` 自身。
  - `clipwire_config_dir()`(`%APPDATA%\clipwire`)、`dirs_next::data_local_dir().join("clipwire")`(`%LOCALAPPDATA%\clipwire`)。
  - スタートアップフォルダ(`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`)、PowerShell プロファイルディレクトリ(`Documents\WindowsPowerShell`、`Documents\PowerShell`)。
  - **自プロセスの実行ファイルのディレクトリ(`std::env::current_exe()` の親)と、ウォッチドッグのフォールバック用バイナリのディレクトリ(ADR-0009 §7 の固定パス `%LOCALAPPDATA%\clipwire\bin`)**。これらへの書き込みは次回再起動時に任意コードを実行させられるため、`%LOCALAPPDATA%\clipwire` の祖先チェックだけでは不十分な場合(`--write-root` がこれらのディレクトリの**配下**を指す場合も含む)に個別に明記する。
  - 「祖先・同一・配下のいずれか」という検査は**起動時の許可ルート自体**に対してだけでなく、**リクエストごとの最終パスにも適用する**(denylist は許可ルートのチェックだけで済ませず、§6 のリクエスト単位の判定にも組み込む。許可ルートの外側は既に拒否されるため冗長ではあるが、許可ルートが広めに取られた場合の belt-and-braces とする)。
- **起動時に、各許可ルートが既存の承認済みターゲット(`registered.toml` の `approved_at` を持つエントリ)の `dir`、または `steps`/`script_file` の argv が参照する絶対パスの祖先・配下にならないかを確認する**。該当する場合は拒否はしないが、起動ログに「`--write-root <root>` はターゲット `<name>` の書き換えを承認なしで許可します」という強い警告を出す(pad2py の実運用は「ビルドターゲットの作業ツリーに書く」ことが目的であり、拒否すると使い物にならないため、警告に留める)。この重複検査は**起動時にのみ**行うため、サーバ稼働中に新しく承認されたターゲットは警告の対象外になる(§1 の制約として明記。改善案として、承認時またはトースト表示時に同じ検査を繰り返すことを検討してよいが、本 ADR の必須要件にはしない)。
- `--enable-write` と許可ルート数、および重複警告の件数は、起動時の `serve-start` 監査イベントに記録する(ADR-0011 §6 の `auto_approve` 警告と同じ扱い)。

### 2. 手動承認運用への影響は正直に書く

- 「`/write` は手動承認運用の意味を壊さない」とは書かない。正しくは: **許可ルートが、既存の承認済みターゲットの `dir` やその参照先と重ならない限り、`/write` は手動承認運用の意味を壊さない。重なる場合、そのターゲットは実質的に自動承認運用相当になる**(§1 の警告が、運用者にこの事実を知らせる)。

### 3. 認可: `check_auth` ではなく `require_auth` と同じ強度

- `/write` は `RouteClass::Clipboard` ではなく、新しい `RouteClass`(トークン必須、または明示的な `--allow-no-token` を要求する `require_auth` を使い、`require_json_content_type` の代わりに §4 の Content-Type 検査を適用する)に乗せる。実装は `src/server/http_surface.rs` の既存 3 グループ構成に 4 番目のグループを足す形で行い、**既存の 3 グループと同様に `reject_origin`/`require_host` のレイヤーより内側(先にマージされる側)に置く**(`build_router` の現在のレイヤー順を保つ)。
- これにより、`--bind-localhost-only` のみ(トークンなし・`--allow-no-token` なし)の構成では `/write` も 403 になり、`/exec` と同じ閉じ方になる。

### 4. CSRF 対策として `Content-Type: application/octet-stream` を必須にする

- `/write` の POST は `Content-Type: application/octet-stream` でなければ 415 で拒否する(他の値も、欠落も拒否)。この型は CORS セーフリストに含まれないため、ブラウザからの `fetch`/`<form>`/`sendBeacon` は必ずプリフライトを要求され、サーバが CORS ヘッダを返さない以上そこで失敗する。
- `reject_origin` はマージ後のルータ全体に効くため `/write` にもそのまま効く。`Host` 許可リストは既定でログのみ(`HostCheckMode::Log`)であり、`/write` にとっての実質的な防御層は「Origin 拒否」+「Content-Type 必須」の 2 層とする。

### 5. パスの指定とヘッダ

- 書き込み先パスは、クエリ文字列ではなく専用ヘッダ `X-Clipwire-Path` に、**パーセントエンコードのみ**で載せる(base64url との二択にしない。曖昧さを残さない)。パーセントエンコードでは `+` はリテラルの `+`(クエリ文字列の `application/x-www-form-urlencoded` 規則とは異なる)であることを明記する。
- パスは絶対パスのみを受け付ける。

### 6. 正規化は二段階(字句チェック → OS 呼び出し → コンポーネント比較)。順序を固定する

字句チェックと OS 呼び出しの順序を取り違えると、OS 呼び出しが親ディレクトリしか正規化しない以上、最終コンポーネント(ファイル名)に対する字句チェックが一度も走らない死んだコードになる(例: `run.py.` が字句チェックの対象から漏れたまま `canonicalize` 後も `run.py.` のままサーバに渡り、`MoveFileExW` 実行時に Windows が暗黙に末尾ドットを除いて `run.py` に書くため、監査ログの記録と実際の書き込み先が食い違う)。そこで次の順序を固定する。

- **(a) 純粋段階(Linux でテスト可能な、OS 呼び出しを伴わない比較・分類のみ)**: ヘッダから**パーセントデコードした直後の生のパス文字列**に対して行う(OS 呼び出しの前)。
  - パーセントデコード後に NUL バイトを含む、または有効な UTF-8 にならない場合は 400。
  - `\\?\` を剥ぎ、`\\?\UNC\` は UNC として扱って拒否する。UNC(`\\server\share\...`)・デバイス名前空間(`\\?\GLOBALROOT\...`、`\\.\pipe\...`)は字面の時点で拒否する(意図しない SMB 接続でユーザーの資格情報を使った認証を引き起こしうるため)。
  - ドライブ相対(`C:foo`)・ルート相対(`\foo`)は絶対パスとして認めず拒否する。
  - `..`・`.` を含むコンポーネントは拒否する。
  - **最終コンポーネント(ファイル名)**に対して: `:` を含むもの(NTFS 代替データストリーム)を拒否する。末尾のドット・空白を含むもの(Windows が暗黙に取り除くため `run.py.` が `run.py` になる)を拒否する。拡張子の有無を問わず予約デバイス名(`CON`、`NUL`、`COM1`〜`COM9`、`LPT1`〜`LPT9`、`CONIN$`、`CONOUT$`、およびこれらに拡張子が付いたもの、例 `CON.txt`)を拒否する。
  - 大文字小文字の畳み込みは、UTF-16 コード単位ごとの単純な ASCII 範囲の大文字化(NTFS の既定短い名前比較と同じ)を使う。Rust の `str::to_uppercase()` は使わない(`ß` → `SS` のように長さが変わる変換があり、異なるパスを同一と誤判定しうる)。
- **(b) OS 呼び出し段階**: (a) を通過したパスの**親ディレクトリ**を `canonicalize`(または開いたハンドルに対する `GetFinalPathNameByHandleW`)で正規化する。各許可ルートと、§1 の denylist 対象ディレクトリは**サーバ起動時に 1 回だけ正規化**して保持する(存在しない denylist 対象ディレクトリは、正規化できないため絶対パスの字面のまま使う。`CLIPWIRE_CONFIG_DIR` 等の環境変数は起動時に解決された値を使い、リクエストごとに再計算しない)。
- **(c) 許可判定(純粋関数、OS 呼び出しなし)**: `正規化された親 + (a) で検証済みの最終コンポーネント` を、正規化済みの許可ルート・denylist 対象ディレクトリと**パス構成要素単位で**比較する(文字列 `starts_with` は `C:\work\pad2py` に対し `C:\work\pad2py-evil` を誤って配下と判定するため使わない)。denylist との比較は祖先・同一・配下のいずれの方向でも一致すれば拒否する(§1 と同じ規則)。
- **(a) と (c) は、`std::path::Path` に依存しない、Windows パスの文字列表現に対するパーサ(例: `typed-path` クレート、または自前の prefix パーサ)として実装し、Linux 上でテストする**(`std::path::Path` は `C:\x` を相対パスとして扱ってしまうため。本リポジトリの既定方針: 判断は純粋関数にしてLinuxでテストする)。(b) の OS 呼び出しだけは Windows 専用コードに残る。
- §7 の一時ファイル→rename 方式により、最終コンポーネントが既存のシンボリックリンク/リパースポイントであっても、`MoveFileEx`(置き換えなしの移動)はディレクトリエントリを置き換えるだけでリンク先を辿らない。したがって最終コンポーネントのリパースポイントチェックは**主たる防御ではなく belt-and-braces**と位置づける(主たる防御は許可ルート配下チェックとコンポーネント単位比較)。ハードリンクはパス比較で検出できない。これは受け入れ、ドキュメントに明記する。
- **TOCTOU**: (b) で親ディレクトリを正規化した後、実際にファイルを作成・置換するまでの間にジャンクションが差し替えられる可能性は理論上残る。これを行えるのは既にそのユーザー権限で動くコードに限られ(手動承認運用ではそれは §2 で「実質自動承認相当」と明記した重複ケースと同じ前提)、新しい権限の発生ではない。実装・テストでは許容し、コード中に一行コメントで明記する。

### 7. 上書き: 既定で「置き換えなしの作成」、`?overwrite=1` で明示的に許可

- 既定では、書き込み先に既にファイルが存在する場合は**409**。実装は `exists()` 確認 → `rename` では**ない**(競合する上、Windows の `rename` は既存ファイルを置き換えてしまう)。`MoveFileExW` を `MOVEFILE_REPLACE_EXISTING` **フラグなし**で呼び、`ERROR_ALREADY_EXISTS`(183)と `ERROR_FILE_EXISTS`(80。`CreateFile` 系 API がファイル存在時に返すコードで、`MoveFileExW` の実装が内部でこちらを返すケースもある)の両方を 409 にマップする。宛先が実行中のプロセスに開かれているなどの共有違反(`ERROR_SHARING_VIOLATION`)も 409 にマップする(「書き込み先が使用中です」)。`?overwrite=1` のときだけ `MOVEFILE_REPLACE_EXISTING` を付ける。
- 一時ファイルは、書き込み先と同じディレクトリ(同一ボリュームで原子的 rename が成立するように)に、ランダムな名前(例 `.clipwire-write-<ulid>.tmp`)で `create_new` して作る。エラー・クライアント切断時は一時ファイルを削除する。クラッシュ等で削除されずに残った `.clipwire-write-*.tmp` は、サーバ起動時に許可ルート配下を一度だけ掃除してよい(無視するだけでも構わない。孤立ファイルが実害を及ぼすことはない)。

### 8. ボディサイズ制限はストリームに対して効くものを使う

- `axum::extract::DefaultBodyLimit` はバッファ系エクストラクタ(`Bytes`/`String`/`Json`)にのみ効き、ストリームする `Body` には効かない。`tower_http::limit::RequestBodyLimitLayer` を使う、またはストリーム中にバイト数を数えて上限(64 MiB)超過時に 413 を返しつつ一時ファイルを削除する。このレイヤーは `/write` を含む**新しい第 4 ルータグループにのみ**適用する(他ルートのボディ制限を変えない)。
- `RequestBodyLimitLayer` を使う場合でも、上限超過はハンドラ内でボディをストリーム中に読むエラーとして現れる(chunked 転送の途中で切られる)。ハンドラはこのエラーを捕捉して 413 にマップし、書き込み中の一時ファイルを削除する処理を必ず経由させる(エラーを上位に伝播させるだけでは一時ファイルが残る)。

### 9. 監査は失敗したら書き込み自体を失敗させる

- `AuditEvent` に `path: Option<String>`・`bytes: Option<u64>`・`sha256: Option<String>`・`overwrote: Option<bool>` フィールドを追加し、新しい `AuditEventKind::Write` を記録する(本文そのものは記録しない)。
- **監査記録に失敗した場合、書き込み自体を失敗させる**(500 を返し、一時ファイルを削除して元のファイルを変更しない)。`/write` の内容は未承認であり、監査が唯一の裏付けになるため、通常のログ書き込み失敗より厳しく扱う。現在の `AuditLog::record` はエラーを握り込んで `()` を返す(`src/audit.rs`)ため、`/write` 用には `Result` を返す経路を別途用意する。
- **手順の順序を固定する**: (1) 一時ファイルへ書き込みを完了する、(2) 監査レコードを書く(失敗したらここで中断し、一時ファイルを削除して 500)、(3) `MoveFileExW` で最終パスへ置き換えなしの移動を試みる。この順序でのみ、「監査に失敗したら元のファイルは一切変更されていない」が成立する。
- `?overwrite=1` のとき、`overwrote`(監査イベント・レスポンス JSON の両方)と 200/201 の判定は、(3) を**まず置き換えなしで**試し、`ERROR_ALREADY_EXISTS`/`ERROR_FILE_EXISTS` を受けてから `MOVEFILE_REPLACE_EXISTING` 付きで再試行する、という手順でのみ確定できる(最初から `REPLACE_EXISTING` を付けて呼ぶと、置き換えが起きたかどうかを呼び出し結果から区別できない)。

### 10. レスポンスと機能通知

- 成功時は 201(新規作成)または 200(上書き)に、書き込んだバイト数と sha256 を JSON で返す。
- `親ディレクトリが存在しない` も `既にファイルが存在する`(既定モード)も、HTTP ステータスは **409** で統一するが、**レスポンス本文に機械判読可能なエラーコード**(例 `{"error": "parent_missing"}` / `{"error": "already_exists"}` / `{"error": "sharing_violation"}`)を含め、クライアントがステータスコードだけでなく原因を区別できるようにする。
- **無効時のステータスコードは、常にマウントされたルートに対する認可拒否として 403 に統一する**(§1 のとおりルート自体は常にマウントするため、404 は「このサーバが本 ADR を実装していない(未知のルート)」の専用の意味になる)。許可ルート外のパスも同じく 403(「このパスは許可ルートの外です」)とし、無効と許可ルート外を本文のエラーコードで区別する。
- `/health` の `features` に `write` を追加する。有効時は `write_enabled: true` と許可ルートの**数**(パスそのものは非認証の `/health` では開示しない)を返す。クライアントは、404(サーバが本 ADR を実装していない)・403(無効、または許可ルート外。本文のエラーコードで区別)・409(親ディレクトリなし、既存ファイル、または共有違反。本文のエラーコードで区別)を区別できる。許可ルートの一覧そのものは、`/write` 自身の 403 エラーメッセージ(認証済み呼び出し元向け)でなら開示してよい(同じトークンで既にその配下に書き込めるため、開示しても権限は増えない)。

## Consequences

- `/write` は既定無効・opt-in・許可ルート限定・トークン必須という、`exec` と同等以上に慎重な扱いになる。許可ルートが承認済みターゲットと重ならない運用では、手動承認運用の意味を壊さない。重なる運用(pad2py が想定するビルド作業ツリーへの書き込み)では、そのターゲットについて実質的に自動承認運用相当になることを、起動時の警告で運用者に明示する。
- README の脅威モデルへの追記は、`/write` が `--enable-write` を指定し、かつ許可ルートが既存ターゲットと重なる場合に限る、と条件付きで書く(本 ADR が Proposed のうちは、脅威モデル本文を書き換えず、本 ADR の Consequences に留める)。

## Alternatives considered

- **当初案(トークン保持者は既にコード実行権限を持つという理由で、`/write` を `/clip` と同じ信頼レベルにする)**: Opus レビューで、この等式が手動承認運用では成立しないこと、`check_auth` がトークン未設定時に開いてしまうことが判明したため撤回した(Context 参照)。
- **`/write` に書き込み先ルートの事前登録(`register` 相当)を要求する**: 許可ルートという軽い仕組みで同じ目的(誤操作の及ぶ範囲を絞る)を達成できるため、`register`/承認という重い経路までは要しない。
- **`/write` の本文を JSON に包み `{"path": "...", "content": "<base64>"}` にする**: まさに pad2py が避けたい base64 エンコードを別の場所で再導入してしまう。raw body + ヘッダのパスの方が一貫し、クオーティング地獄を増やさない。
- **正規化を「純粋関数のみ」で済ませる**: ジャンクション・シンボリックリンク・8.3 短縮名を見逃す。「`canonicalize()` のみ」で済ませる: Linux でテストできず、ロジックの検証が手薄になる。両方必要という結論に至った(§6)。
