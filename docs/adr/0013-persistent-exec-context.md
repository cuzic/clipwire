## Context

pad2py からの要望 (c): `exec` のたびに新しいプロセスが起動するため、pywinauto で一度見つけたウィンドウ/コントロールのオブジェクト参照を次の `exec` に持ち越せない。ウィンドウ探索 → クリック → 結果確認 → 次のクリック、という対話的な UI 自動化が、呼び出しごとにゼロから要素探索をやり直す羽目になる。要望としては「Jupyter kernel のような、状態を持つ長命プロセスに複数回の `exec` 呼び出しをつなぐ」経路。

pad2py 自身が「余裕があれば」「急ぎではない」と位置づけており、ADR-0012(a)/(b) より明確に大きい設計変更になる。

**既存基盤がそのまま使えない理由**: `Runner::spawn`(`src/runner/mod.rs`)は `command.stdin(Stdio::null())` を固定しており、生成した子プロセスへの書き込み経路が最初から存在しない。`JobStatus`(`src/jobs.rs`)の状態機械も「メインプロセスの終了で完了する一回限りの実行」を前提にしており、「複数ターンにわたって生き続け、ターンの合間はアイドルする」状態を表現できない。つまり (c) のターンの入出力(stdin/stdout とのやり取り)は `Runner`/`JobHandle::wait` の改修ではなく、**並行する別サブシステム**(`PersistentContextRegistry`)になる(改訂4: ただし後述 §3 のとおり、ライフサイクル・相互排他・`/jobs` での可視性は `JobRegistry` にそのまま乗せる。別サブシステムになるのはターン I/O の部分のみで、`JobRegistry` 全体を置き換えるわけではない)。

### 当初案の誤り(Opus レビューで判明。改訂1で修正)

当初案は「承認されるのは起動スクリプトという殻だけで、以後何を実行するかは承認の対象外になる」という性質を、「既存の Rhai `script`(`run`/`run_ok` で任意の子プロセスを起動できる)と**同じ信頼モデル**」と説明していた。これは誤りで、次の点で本質的に異なる。

- 承認済みの Rhai `script` 本文は**それ自体がプログラム全体**であり、`exec` が運ぶ呼び出し側からの入力は `name`/`timeout`/`detach` のみで、コードそのものは一切運ばない(`src/server/exec.rs`)。
- 永続コンテキストのラッパーは、承認後に**呼び出し側が実行時に選ぶ、未承認・未ハッシュの任意コードを無期限に受け取り続ける汎用コードオラクル**になる。これは ADR-0004 が「実行時に任意文字列を差し込めると承認が無意味になる」として明確に却下した構図そのものであり、ADR-0004 がまだ `choices`(列挙的な選択肢)程度しか認めていないのに対し、本 ADR は無制限のコード実行に踏み込む。
- したがって、手動承認運用でラッパーを 1 回承認することは、**そのターゲットについて以後、実質的に自動承認運用と同じ状態にする**ことを意味する。これは「殻だけ承認する」という説明が想像させるものより重い。

本 ADR は、この性質を隠さずに正面から設計する。

## Decision(T9.3 PoC の結果を改訂3まで反映済み。残る未決点は Status 参照)

### 1. 永続モードはハッシュ束縛された定義の一部にする

- `script_file`(ADR-0012)に `persistent: bool`(または専用の `persistent: PersistentDef { .. }`)フィールドを追加し、**`CanonicalTarget` のハッシュに含める**。
- 永続起動(§2)は、`persistent` フラグを伴って承認されたハッシュに対してのみ許可する。通常の `script_file` として承認された定義を永続モードで起動することはできない(例えば `interpreter: ["python", "-i"]` のような対話フラグを後から足して永続起動に流用する、という迂回を防ぐ)。
- ADR-0006 のレビュー画面(トースト/承認 UI)は、`persistent` が立っている定義を**明示的に** 「このターゲットは、承認後に無期限の任意コード実行を許可します」のような強い文言で表示する(通常の `script_file`/`steps`/`script` と同じ扱いにしない)。
- **ウォッチドッグのフォールバックバイナリ対応が前提**(ADR-0012 §1 と同じ理由・同じ制約): `script_file` を知っていても `persistent` を知らない旧バイナリが `registered.toml` を書き戻すと、このフィールドが黙って失われ、該当ターゲットはハッシュ不一致で動かなくなる。本フィールドも、フォールバック用バイナリが `persistent` を認識するバージョンに更新されるまで出荷しない。

### 2. 起動とプロトコル

- 永続コンテキストは ADR-0012 の `script_file`(`persistent: true`)をラッパースクリプトの起動として使う。ラッパーは stdin から 1 行 1 JSON ターンを読み、受け取ったコードを実行し、stdout に 1 行 JSON で結果を返す。
- **プロトコル応答は stdout を直接使わず、起動直後に複製した専用の fd に流し、fd 1 は恒久的に devnull へ向け直す**(T9.3 PoC 項目1・5.1 で判明。改訂3で初版を書いたが、その版は実装(`wrapper.py`)と不一致で「ターン外は常にログ側」になっていなかったことが改訂3への再レビューで判明。改訂4で実装・テストともに修正。改訂5で「ログ側(fd 2 への dup2)」から「devnull」に変更): ラッパー起動直後、まず `proto_fd = os.dup(1)` で応答用の fd を退避し、続けて fd 1 を**恒久的に** devnull に向け直す。各ターンの実行中だけ、fd 1/2 を一時ファイルへ `os.dup2` で向け直し(Python レベルの `sys.stdout`/`sys.stderr` だけでなく、同じ fd を継承したサブプロセスや生の `os.write(1, ...)` の出力も含めて漏れなく捕捉するため)、ターン終了時に**devnull**(プロトコル用パイプではない)に戻す。改訂3で最初に書いた版は、ターン終了時に戻す先が誤って「プロトコル用パイプ」のままだったため、ターンの外(バックグラウンドスレッド、ターン終了後も動き続ける処理)で fd 1 に書かれたものがそのままプロトコルの改行区切り JSON フレーミングを壊していた。改訂4ではこの戻し先を「fd 2(ログ側)への dup2」としたが、**fd 1 と fd 2 を dup2 で恒久的に同一のパイプへ別名付けすると、ターン内で `subprocess.run()` を呼ぶテストが Windows 実機 CI でだけハングすることが判明した**(原因は特定できていないが再現性があり、恒久リダイレクト先を独立した devnull に変更したところ解消した。T9.3 evidence 項目1(続き)参照)。したがって恒久リダイレクト先は fd 2 とは独立した devnull とし、fd 1/fd 2 を外側では決して同一のパイプへ別名付けしない。**レスポンス自体は `proto_fd` 経由で書く**(fd 1 ではない)。本実装でターン外の書き込みをログとして観測したい場合は、devnull ではなく診断用の別ファイル/パイプへ向けることを検討する(fd 2 との別名付けは避ける)。**fd 0(標準入力)の番号も同じ理由(§3 改訂7 参照)で恒久的に devnull へ向け、実際のプロトコル入力は fd 0 とは独立した non-inheritable な fd から読む**(Windows で `subprocess` が `stdin=None` のとき触れるのは fd 0 の番号そのものであり、fd 1 と同じ理屈がそのまま当てはまるため)。この修正を `docs/tasks/evidence/poc/t9.3/wrapper.py` に適用し、ターン終了後にバックグラウンドスレッドが書き込むケースの回帰テスト(`tests/t9_3_persistent_context_poc.rs` の `poc_item1_late_write_after_turn_does_not_corrupt_next_turns_framing`)を追加して確認した(修正前のコードに戻すと実際に失敗することも確認済み)。**出力の到着順序は保証しない**(print・サブプロセス継承・生の fd 書き込みの間で、各ライターの flush タイミングに依存する。ソースコード上の順序と一致しないことがある。pad2py のデバッグ用途(どのクリックの後にどのログが出たか)に影響するため、呼び出し側に明記する)。
- 子プロセスの `stdin` を `Stdio::piped()` にする新しい spawn 経路を `Runner` とは別に用意する(既存 `Runner::spawn` の `Stdio::null()` 前提は変更しない。ADR-0009 の対象外)。**stderr は継続的に排出する**(ADR-0009 のリレー機構を再利用する。排出せずパイプバッファが埋まると子がブロックし、ターンがハングする。ADR-0009 §1 が同じ理由でリレー方式を採用した)。
- サーバ側は**コンテキストごとに 1 ターンを直列化**する(同一コンテキストへの並行 `exec` は 409 で拒否。stdin/stdout の 1 対 1 対応を壊さないため)。
- **ターン送信エンドポイントは `RouteClass::Protected` とする**(`require_auth` + JSON Content-Type 必須)。ターンの本文はコードそのものであり、ADR-0014 の `/write`(ファイルのバイト列。Content-Type 不問)とは性質が違う。リクエストボディは `{"code": "..."}` のような JSON で運ぶ。

### 3. ライフサイクル・失効・監査

- 新しいレジストリ(`PersistentContextRegistry`。`JobRegistry` とは独立)が、コンテキスト ID・バッキングプロセスの `ChildIdentity`・最終アクセス時刻・起動に使った定義ハッシュ・起動時の `canonical_json(target)` を管理する。
- **毎ターン、`exec`(単発実行)と同じ再検証を省略なしで行う。mtime ゲートは最初の実装では入れない**(改訂4。改訂3時点の mtime ゲート設計は Opus レビューで「release ビルドでは約 19ms(T9.3 evidence 項目5)であり、pywinauto の 1 ターン(要素探索・UIA 呼び出し)は通常それより 1 桁以上長いので、最初の実装でキャッシュの複雑さ(identity の取り方を Windows で間違える、比較キーの一部を落とす等、新しい不具合の入り口になる)を負う理由がない」と指摘され撤回): `registered.toml` から対象ターゲットの現在のハッシュを読み、`approved/<hash>.json` を読んで sha256 を再計算し、起動時に保持した canonical 定義と一致するか確認する(`Store::verified_target`、通常 `exec` が使う経路そのもの。永続コンテキスト専用の再検証経路は作らない)。不一致・不在が判明すれば、そのターンを拒否してコンテキストを終了させる。デバッグビルドでの実測は 1 ターンあたり約 300ms、release ビルド(Linux 開発機、`opt-level=3, lto=true`)での実測は約 19ms(T9.3 evidence 項目5)。実機 Windows(`dragonflyg4`。ウイルス対策のリアルタイムスキャンが `registered.toml` の読み込みに掛かる可能性がある)での実測はまだ無く、本実装着手前に取る。**`registered.toml` の再パースを `fs::metadata` の `(ファイル identity, size, mtime)` でスキップする最適化は、実測で実際に応答性を損なうことが分かってから、`approved/<hash>.json` 側の検証は対象にしないという制約(改訂3で判明。ADR-0010 §3 が「改ざん・部分書き込みの検出」と位置づける検査を弱めるため)を保ったまま追加検討する**(Alternatives 参照)。
- **アイドルタイムアウトに加えて絶対寿命を設ける**。アイドルタイムアウト単独では、30 分おきにポーリングするだけのクライアントがコンテキストを無期限に生かし続けられる。絶対寿命は既定 4 時間、起動時の設定で変更可能にする(上限は設けない。無期限の任意コード実行を許可すること自体が §1 で明記した仕様であり、絶対寿命は「ポーリングだけで無期限に生かし続けられる」ことを防ぐためのものであって、信頼境界そのものではない。既定値は pad2py の実際の作業セッションの長さに応じて調整してよい、Accepted を止める理由にはしない。改訂5)。絶対寿命を超えたら、アイドル状態に関わらず終了させる。
- **ターンごとのタイムアウトと kill エンドポイントを設ける**。UIA 呼び出しがモーダルダイアログで止まるなど、ターンがハングする可能性は pywinauto の用途では現実的に高い。ハング中のターンは「進行中」である限りアイドルタイムアウトを起動させないため、ターン単独のタイムアウト(ADR-0003 の上限に揃える)でコンテキストを終了させる仕組みと、`DELETE /contexts/<id>` のような明示的な kill エンドポイントの両方が必要。
- **Windows での終了: 直接の子プロセス kill で出荷し、孫プロセスの残存は T5.1/T6.2 と同じ既知の制約として扱う**(改訂3。T4.4 待ちだった改訂2の方針を撤回): `src/runner/windows.rs` の `OsProcessGroup` は現時点でスタブで(`spawn_in_group` は素の `command.spawn()`、`terminate()` は何もしない)、`JobHandle::terminate()` も Windows では直接の子プロセスにのみ `child.kill()` する。アイドルタイムアウト・絶対寿命・kill エンドポイントでラッパーを終了させても、**ラッパーが起動した孫プロセスは現状の Windows 実装では道連れにならず残り続ける**(実機 `dragonflyg4` で、親プロセスのみを終了させ孫プロセスが生き残ることを直接再現済み。`docs/tasks/evidence/t9.3-persistent-context-poc.md` 項目3)。これを理由に本実装を T4.4(Job Object)の完了まで止めるのは一貫していない: 同じ「Windows では子孫を倒せない」制約を抱えたまま、T5.1(timeout)・T6.2(`--detach`/`kill`)は既に「孫プロセスの Windows ツリー kill は T4.4 待ち」として出荷されている(`docs/tasks/README.md`)。加えて、Job Object は pywinauto の用途に対して必要条件でも十分条件でもない: pywinauto が操作する対象アプリは、既に起動済みのアプリや COM 経由で別ホストから起動されるプロセスなど、ラッパーの子孫でない場合が多く Job に入らない(不十分)。逆にラッパー自身が `Application().start()` で起動したアプリは Job に入り、`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を使うとコンテキスト終了時に**操作対象として残したいアプリまで落ちる**副作用がある。したがって「T4.4 を待てば終了処理が正しくなる」とは言えない。**停止させるべき安全要件は「任意コードの受付口を止めること」であり、これは (a) サーバが stdin のパイプを閉じ、ラッパーが EOF を検知して自分から終了する、(b) 直接の子プロセスに対する `child.kill()` を併用する、の組み合わせで今すぐ満たせる**(改訂7で訂正: 当初「直接の子への `child.kill()` で足りる」としていたが、`script_file` の `interpreter` が §3 で述べる中継プロセスを経由する構成では、直接の子は中継プロセスであり、`child.kill()` が倒すのは中継プロセスだけでラッパー自身は生き残ってしまう。実際に受付口を止めているのは (a) の stdin を閉じることであり、これは中継プロセスの有無に依存しない。(b) は中継プロセスを含めた OS 上のプロセスツリーを速やかに片付けるための追加の手段であって、受付口を止める決定的な手段ではない)。残る孫プロセスのリソースリークは T5.1/T6.2 と同種の既知の制約として README/本 ADR に明記する。**「T4.4 完了時に自動的に改善される」とは言い切らない**(改訂4で訂正。T4.4 自体が入っても、上記の `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` の副作用があるため、永続コンテキストのラッパーを kill-on-close の Job に入れるか、breakaway させて Job 自体には入れないかは、pad2py の実際の pywinauto 運用(操作対象アプリをコンテキスト終了時に一緒に落としてよいか)の確認結果で決める別の判断であり、T4.4 の完了だけでは自動的には決まらない。この判断は本実装着手前の未決事項として残す。Status 参照)。
- **クラッシュ検出**: ターンの合間にプロセスが終了していた場合、次の `exec` 呼び出しは「コンテキストは既に失われている」ことを明確なエラーで返す(ハングさせない)。
- **サーバ再起動時: stdin の読み取りをターン実行とは別スレッドで行い、EOF を受けたらハング中でも即座に終了する**(改訂4で要件化。改訂6で一度「親 PID の生存ポーリング」に置き換えたが、改訂7で撤回し stdin EOF 方式に戻した。経緯は次段落): ターン実行スレッド自身が stdin を読む設計だと、ターンがハング中(pywinauto のモーダルダイアログ待ちなどで現実的に起こる)はサーバの消滅に気づけない。この場合、再起動後の `JobRegistry::open` はこのラッパーの子プロセスがまだ生きているため `Orphaned` として復元し、`persistent: true`(常に `Concurrency::Reject`)の席を握り続ける。`decide_kill`(`src/jobs.rs`)は `JobControl` が無い job には `Finished` を返すため、`/jobs/<id>/kill` ではこの Orphaned job を倒せず、`DELETE /contexts/<id>` もコンテキストのメモリ上の状態が再起動で消えているため対象を指せない。結果、**ハングしたラッパーが自然に終了するまで、そのターゲット名で新しい永続コンテキストを起動できない**。
  - **当初の実装(stdin を専用スレッドでブロッキング読み取りし、EOF で `os._exit()`)は Windows で確実にハングすることが実機 CI で判明した**(改訂6): ターン内で `subprocess.run()`/`subprocess.Popen()` を呼ぶテストが、Windows でだけ 10 秒タイムアウトで必ず失敗した。fd 1/fd 2 の実装(別名付け先・devnull 化・`set_inheritable`)や stdin の読み取り方法(`sys.stdin` 経由・`os.read()` 直接)を何通り変えても解消せず、スレッドを完全に無効化すると(EOF 検知の要件を諦めれば)初めて解消した。
  - **改訂6の回避策(親 PID の生存ポーリング)は、改訂6自体への再レビューで launcher 構成に対する欠陥が判明し撤回した**: `script_file` の `interpreter`(例 `["python"]`)が、venv の `python.exe`(リダイレクタ)・`uv run`・py ランチャーのような**ラッパーを子として起動して待つだけの中継プロセス**を経由する構成は、pad2py の運用で自然にありうる。この場合ラッパーの OS 上の親はサーバではなく中継プロセスになり、サーバが死んでも中継プロセスは死なない(Job Object が無く道連れにならず、自分の子の終了をただ待ち続ける)ため、`getppid()` ベースの監視では永久にサーバの消滅を検知できない。
  - **改訂7: ハングの機序を特定し、stdin EOF 方式に戻した**。仮説: CPython の `subprocess`(Windows)は `stdin=None` のとき `GetStdHandle(STD_INPUT_HANDLE)` を子の stdin として渡すため、子プロセスを起動するたびに「読み取り中のパイプそのもの」(= fd 0)に触れる。別スレッドがまさに fd 0 を `ReadFile` でブロッキング読み取り中だと、Windows の同期 I/O 絵の直列化によりこれが衝突する(API レベルの正確な機序は実証できていないが、下記の検証で一貫して再現した)。fd 1 に対して行った devnull 化(§2)と同じパターンを fd 0 にも適用: 起動直後に `proto_in = os.dup(0)`(non-inheritable)でプロトコル入力を退避し、fd 0 の**番号**自体は恒久的に devnull へ向け直す。ラッパー内のプロトコル読み取りは `proto_in` から行い、ターン内で起動されるサブプロセスは fd 0(devnull)を継承するため、読み取り中のパイプのファイルオブジェクトには一切触れない。**この変更後、ターン内で subprocess を起動するテストが Windows 実機 CI で安定して通るようになった**(run 41771067481)。これにより stdin EOF 方式に戻せる: パイプの**書き込み側**を持つのはサーバだけなので、`interpreter` に何段の中継プロセスが挟まっていても、サーバが死ねば確実に EOF になり、launcher 構成の問題も同時に解決する。`docs/tasks/evidence/poc/t9.3/wrapper.py` に実装し、以下を回帰テストで確認した: (a) ハング中のターンに対しても EOF 後 5 秒以内に終了すること(`poc_eof_during_a_hung_turn_still_exits_promptly`)、(b) 中継プロセスを生かしたまま(kill せず)テスト側のパイプだけを閉じても終了すること(`poc_eof_propagates_through_an_intermediate_relay_process`)、(c) ターンの外(メインスレッドが次のターンを待っている間)で前のターンが残したバックグラウンドスレッドが subprocess を起動してもハングしないこと(`poc_subprocess_from_background_thread_between_turns_does_not_hang`)。
  - サーバ再起動後の持ち越しはしない(呼び出し側が再度コンテキストを起動する)。**Orphaned のまま残る席を `JobRegistry` 側から能動的に回収する手段(`decide_kill` の拡張等)を用意するかどうかは未決**(通常の detach ジョブにも共通する既存の穴だが、永続コンテキストは常に Reject かつハングしやすいため顕在化しやすい。Consequences 参照)。
- **監査**: `AuditEventKind` に `ContextStart` / `ContextTurn` / `ContextEnd` / `ContextKilled` を追加する。`ContextTurn` にはターン本文の sha256 とバイト数を記録し、本文そのものは専用ログに追記する(配置は次段落)。**監査記録に失敗したターンは拒否する**(承認が「殻」だけで、以後の内容は監査だけが唯一の裏付けになるため、通常のログ書き込み失敗より厳しく扱う)。現在の `AuditLog::record` はエラーを握り込んで `()` を返す(`src/audit.rs`)ため、コンテキストのターン監査には `Result` を返す別経路を用意する(ADR-0014 §9 の `/write` 監査と同じ要件)。
- **コンテキストのログは `jobs/` を流用しない**。`jobs/<job-id>/` は `JobRegistry` が `meta.json` を持つディレクトリとして管理し、`prune()` もそれを前提に動く。コンテキストは `meta.json` を持たないため、`jobs/<context-id>/` に置いても `JobRegistry::open`(起動時の読み込み)はそれを素通りし、`prune()` も対象として認識せず、ターン本文(`turns.jsonl`)が無制限に積み上がる。コンテキスト専用のルート(例: `dirs_next::data_local_dir().join("clipwire").join("contexts").join(<context-id>)`。`%LOCALAPPDATA%` 側。ジョブログや自己更新バイナリと同じ「ローミングしなくてよい」側に置く。`%APPDATA%` 側の `clipwire_config_dir()` はターゲット定義・承認レコードという小さく重要な状態専用に保つ)を設け、独自の保持件数・サイズ上限で刈り込む。
- **`persistent: true` のターゲットは通常の単発 `exec` では起動できない**(改訂3で追加。T9.3 PoC 項目4 の議論を踏まえた前提の確定): ラッパーは stdin の `readline()` で待ち受ける設計のため、`Runner::spawn` の `Stdio::null()` で単発起動しても EOF を即座に受け取って終了するだけで意味がない。`into_exec`(`src/config.rs`)の段階で `persistent: true` の `script_file` を単発 `exec` 経路に渡すことを禁止する。これにより、1 つのターゲット名は常に「通常の `exec`/`steps`/`script_file`」か「永続コンテキスト」のどちらか一方の経路でしか動かなくなり、相互排他が必要な場面は「同名ターゲットに対する永続コンテキストの多重起動」と「実行中の通常ジョブが残っている間に同名ターゲットが永続定義で再承認された直後の起動」に縮小される。
- **相互排他の実装場所: 永続コンテキストが `JobRegistry` に「席」を取る**(改訂3。シェアされた `HashSet` を exec ディスパッチ層に新設する改訂2の案を撤回): `Concurrency::Reject` は `JobRegistry::start`(`src/jobs.rs`)の内部で、`JobRegistry` 自身が持つ `jobs` マップを線形走査して実装されている。改訂2の「共有 `HashSet`」案は、(1) `JobRegistry::open` が起動時に復元する `Orphaned`(再起動前に生きていた子)の状態が見えず、サーバ再起動直後に通常 `exec` 側は弾かれるのに永続コンテキスト側は素通りする非対称が生じる、(2) `finish`/`kill`/`Lost` 遷移・detach(即座に 202 を返す)・panic など `JobRegistry` のライフサイクル全経路に解放フックを重複して持つ必要があり、片方だけ更新されると集合がリークしたまま 409 を返し続けるか、相互排他そのものが壊れる、という二重管理の問題を抱える(Opus レビューで指摘)。代わりに、永続コンテキストの起動時に `JobRegistry::start(target, hash, requester, Concurrency::Reject)` を呼んで通常の job と同じ「席」を取り、コンテキストが生きている間はその job を `Running` のまま保持し、終了時に `finish`(または kill 経路)で閉じる。ターンの入出力(stdin/stdout とのやり取り)は `JobHandle::wait` を使わず `PersistentContextRegistry` が持つ。これにより Reject 判定・`Orphaned` 復元(`set_child` で `ChildIdentity` を記録すれば再起動後も検出される)・`/jobs` 一覧での可視性・`prune` がすべて既存実装のまま効き、新しい共有集合は不要になる。**`script_file` の `interpreter` が中継プロセス(§3)を経由する構成では、ここで記録する `ChildIdentity` は中継プロセスのものになる**(`Runner`/`JobHandle` が直接 `spawn` するのは `interpreter` の最初の要素であり、実際のラッパーはその子孫になるため)。`process_alive` によるプロセス生存確認・Orphaned 復元は、したがって中継プロセスの生存を見ることになるが、中継プロセスは(サーバが死んでも)ラッパーより先に終了することはないと想定できるため、Reject 判定・復元の正しさには影響しない。`persistent: true` のターゲットは、保存されている `concurrency` フィールドの値に関わらず常に `Concurrency::Reject` 相当として扱う(1 ターゲットに対し同時に複数の永続コンテキストを許す使い方は想定しないため、`Concurrency::Allow` との組み合わせを個別に定義する必要がない)。`check`/`list`/`steps`(Rhai `run` 等)がターゲット名を参照する既存の経路についても、`persistent: true` ターゲットは単発 `exec` と同様に扱う(§1 の `into_exec` での禁止に揃える)。
- **「席」方式の API 設計(改訂4で未決事項として追加、改訂5で決定)**:
  - **kill の入口は1つに合流させる**: 永続コンテキストも `JobControl` を登録し、`/jobs/<id>/kill` と `DELETE /contexts/<id>` のどちらを叩いても同じ終了処理(ラッパーへの終了要求 → `finish`)に合流する。`/jobs` 側を 409 で拒否する案は、ユーザーが `clipwire jobs` で `Running` と見えている job を `clipwire kill` で倒せないという驚きを生むため採らない。kill の実装自体は1箇所で済み、改訂3で避けた二重管理が kill の入口で再発することもない。
  - **`finish` に渡すステータスは既存の `JobStatus` にそのまま寄せる**(新しい規則を作らない): 呼び出し側の明示的終了(`DELETE`/`kill`)は `Killed`、アイドルタイムアウト・絶対寿命・ターンタイムアウトは `Timeout`(T5.1 と同じ表現、exit code 124)、再検証失敗(承認取り消し・改ざん検出)は `Failed`(監査に理由を残す)、ターンの合間にラッパーが自分で終了・クラッシュした場合は `Failed`(exit code が取れれば)または `Lost`(取れなければ)、サーバ再起動で EOF 終了した場合は既存の復元経路どおり再起動後の `open` が `Lost` にする。`prune` の削除順(`failure()`/`detached` で変わる、`src/jobs.rs`)への影響も、既存の通常ジョブの扱いと揃うため新たな整合作業は不要。
  - **ログ API は 404/空ではなく、場所を案内するエラーを返す**: 永続コンテキストの job に対する `/jobs/<id>/logs` や follow は、ログが `jobs/` 側ではなく `contexts/<id>/` 側に置かれていることを示すエラー(例: 409 + 説明文)を返す。空を返すと「ログが無い」のか「場所が違う」のかが区別できないため避ける。

### 4. README 脅威モデルへの反映

- 「殻だけ承認する」という表現ではなく、**「`persistent: true` を承認することは、そのターゲットについて以後、無期限に自動承認運用相当の状態を作ることである」**と明記する。ADR-0004 への参照を付け、なぜこの例外を認めるか(pad2py の専用 VM での運用であり、既に `--auto-approve` を実運用の前提とするモードが存在すること)を Consequences に書く。

## 実装前に PoC で確認する項目(T9.3、2026-11-03 完了。結果は `docs/tasks/evidence/t9.3-persistent-context-poc.md`)

1. **確認済み(改訂4・7で修正)**: ラッパー内での stdout/stderr 捕捉(§2)が、pywinauto のようにネイティブ拡張やサブプロセスを経由するライブラリの出力も含めて漏れなく拾えること。fd レベルの `dup2` 退避で確認(print/サブプロセス継承/生の `os.write(1, ...)` のすべてを捕捉)。ただし出力順序の保証はない。プロトコル応答を fd 1 に相乗りさせない設計(§2)に加え、**fd 1 をターンの外では恒久的に devnull へ向け直す**修正を適用し、ターン終了後のバックグラウンドスレッドの書き込みがフレーミングを壊さないことを回帰テストで確認した(改訂3時点ではこの恒久リダイレクトが実装に入っておらず、「確認済み」という記述が実態と不一致だった)。改訂7で fd 0 にも同じ devnull 化を適用している(§2・§3)。
2. **確認済み(改訂7で終了検知の方式が変わったため再確認)**: `Stdio::piped()` の子に対する 1 ターンのフレーミング(改行区切り JSON)が安定して届くこと(200KB 超の出力・50 ターン連続送信・ターンを跨いだ状態保持・ハング中ターンでの stdin EOF 検知・中継プロセスを経由しても EOF が伝わること・ターンの外でのバックグラウンドスレッドからの subprocess 起動が妨げられないことを Linux で確認、16 バイト〜8 MiB の単一行ペイロードを実機 `dragonflyg4` で直接確認、同一テストを Windows CI(最終的に全6テストが緑になった run 41771067481)でも確認)。
3. **判明(改訂3で結論変更)**: 比較対象の Windows Job Object 統合(T4.4)自体が未実装(`src/runner/windows.rs` はスタブ)であり、アイドルタイムアウト・絶対寿命での終了は孫プロセスを道連れにしない。ただしこれは T5.1/T6.2 が既に抱えて出荷している既知の制約と同種であり、Job Object は pywinauto の対象アプリに対して必要条件でも十分条件でもないため、T4.4 を本実装の前提にはしない(§3)。
4. **判明(改訂3で結論変更、改訂5で API 設計を決定)**: `Concurrency::Reject` と永続コンテキストの相互排他は、exec ディスパッチ層への共有集合ではなく、永続コンテキストが `JobRegistry::start` で通常の job と同じ「席」を取る形で実装する。これには前提として `persistent: true` ターゲットの単発 `exec` を禁止する必要がある(§3)。「席」方式に伴う kill の入口・`finish` のステータス対応・ログ API の振る舞いも決定済み(§3)。
5. **release で約 19ms、mtime ゲートは最初の実装では見送り(改訂4)**: デバッグビルドでの実測(約 300ms)は release ビルド(Linux 開発機)では約 19ms に下がった(`docs/tasks/evidence/t9.3-persistent-context-poc.md` 項目5)。pywinauto の 1 ターンは通常これより 1 桁以上長いため、mtime によるキャッシュは最初の実装では入れず、実測で必要になってから追加検討する(§3、Alternatives)。追加する場合も、承認完全性の検証(`approved/<hash>.json` 側)はゲートの対象にしない。

## Alternatives considered

- **(改訂6で追加、改訂7で撤回)サーバの生存検知を `os.getppid()` の生存ポーリングで行う**: stdin を別スレッドでブロッキング読み取りする設計が Windows でハングする問題への回避策として改訂6で採用したが、`script_file` の `interpreter` が venv のリダイレクタ・`uv run`・py ランチャー等の中継プロセスを経由する構成では、ラッパーの OS 上の親がサーバではなく中継プロセスになり、サーバが死んでも中継プロセスは死なないため機能しないと再レビューで判明し撤回した。fd 0 の devnull 化(§2・§3)でハングの根本原因を解消できたため、stdin EOF 方式(中継プロセスの有無に依存しない)に戻せた。

- **(改訂3で追加、改訂4で最初の実装からは見送り)`registered.toml` の再パースを mtime でゲートする**: デバッグビルドでの実測(約300ms)を根拠に改訂3で必須の設計変更として採用したが、release ビルドでの再測定(約19ms。T9.3 evidence 項目5)の結果、pywinauto の1ターンより1桁以上短いコストであることが分かった。キャッシュの導入はそれ自体が新しい不具合の入り口になる(Windows での file identity 取得を誤る、比較キーの一部を落とす等)ため、実測で実際に応答性を損なうと判明してから追加検討する任意の最適化に位置づけを下げ、最初の実装には入れない。

- **「Rhai `script` と同じ信頼モデル」という当初の説明**: Opus レビューで、Rhai `script` には呼び出し側からのコード入力チャネルが存在しないため等価ではないと指摘され撤回した(Context 参照)。
- **`JobStatus` 自体に「生存中・次のターン待ち」という新しい状態を追加し、`JobHandle::wait`/`wait_cancelable` もターンごとに戻ってくる非終了プロセスに対応させる**: `Runner::spawn` の `Stdio::null()` 前提、`wait` 系の「プロセス終了を待つ」設計が、ターンごとに戻ってくる非終了プロセスとかみ合わず、既存のジョブの一回限り実行という不変条件を壊す。この全面拡張は却下するが、**`JobRegistry::start`/`finish` による「席」の確保・解放(状態・相互排他・可視性)だけは、改訂3・4 で部分的に採用した**(§3)。却下したのは `JobHandle::wait` 系の拡張であり、`JobRegistry` 自体ではない。
- **ターンごとに個別ハッシュ承認を要求する**: 対話的な制御フロー(FSM・コルーチン的な実行)という要望の本質(呼び出し側が実行時に次の一手を決める)と矛盾する。要求するなら永続コンテキスト自体を提供する意味がなくなる。
- **(改訂2で追加、改訂3で撤回)本実装の着手を T4.4(Job Object)の完了まで待つ**: 改訂2はこれを既定方針としたが、Opus レビューで (1) 同じ制約を抱える T5.1/T6.2 が既に出荷済みであることと一貫しない、(2) Job Object は pywinauto の対象アプリに対して必要条件でも十分条件でもなく、`KILL_ON_JOB_CLOSE` には操作対象アプリを落とす副作用もある、と指摘され撤回した(§3)。
- **(改訂2で追加、改訂3でも不採用のまま)ラッパー自身が子孫 PID を自己追跡して kill する**: T4.4 と独立に進められる利点はあるが、ラッパー(Python)側に子孫追跡という追加の責務を持たせることになり、pywinauto が起動する子孫(既に起動済みのアプリ、COM 経由のプロセスなど)をラッパーが全て把握できるとは限らず、Job Object 案と同様に不完全。追加の複雑さに見合わないと判断し、既定案は「直接の子 kill + 既知の制約として明記」(§3)とした。
- **(改訂2で追加、改訂3で撤回)相互排他をシェアされた `HashSet` として exec ディスパッチ層に新設する**: `JobRegistry` の `Orphaned` 復元状態が見えず、ライフサイクル全経路(finish/kill/lost/panic/detach)への解放フックの重複が必要になる二重管理になることが Opus レビューで指摘され撤回した。永続コンテキストが `JobRegistry::start` で席を取る方式(§3)に変更した。

## Consequences

本実装着手前に解消が必要な設計論点ではなく、実装時に対応する、または運用上の既知の制約として受け入れるもの(改訂5で Status から移動):

- **Orphaned のまま残る席の回収**: stdin EOF の別スレッド検知(§3)で「サーバ再起動後にラッパー自身が気づいて終了する」経路は塞いだが、**ターン実行スレッドが GIL を解放しないネイティブ呼び出しでブロックしている間は、stdin 読み取りスレッド(Python コード)自体が GIL を再取得できず、EOF を検知済みでも `os._exit` に進めない**(「OS レベルのハング」ではなく、Python の GIL というインタプリタレベルの制約)。`time.sleep` や、pywinauto が主に使う pywin32 の `SendMessage`・ctypes/`WinDLL` 経由の呼び出しは通常 GIL を解放するため該当しないと考えられるが保証はなく、`ctypes.PyDLL` 経由や GIL を握ったままブロックする C 拡張ではこの限界に当たる。通常の detach ジョブにも共通する既存の穴だが、永続コンテキストは常に Reject かつこの種のハングが起きやすい用途(pywinauto)を想定しているため顕在化しやすい。Windows で T4.4(Job Object)が入れば、サーバの終了と同時に OS がラッパーを倒せる経路になり、この GIL の限界と無関係に解決できる。それまでは既知の制約として受け入れる(運用上は、ハングしたラッパーの手動終了が必要になる場合がある)。
- **`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` の副作用**: T4.4(Job Object)が入ったとき、永続コンテキストのラッパーを kill-on-close の Job に入れるか、breakaway させて Job 自体には入れないかは、pad2py の実際の pywinauto 運用(操作対象アプリをコンテキスト終了時に一緒に落としてよいか)を確認してから決める。T4.4 自体の実装は別タスク(`docs/tasks/04-runner.md` T4.4)で、本 ADR の実装とは独立に進めてよい。
- **release ビルドでの再検証コストの実測**: Linux 開発機では約19ms(T9.3 evidence 項目5)。実機 Windows(`dragonflyg4`。ウイルス対策のリアルタイムスキャン等、Linux と異なる要因があり得る)での実測は本実装時に取る。mtime ゲート(Alternatives)を追加するかどうかは、その実測を踏まえて判断する。
