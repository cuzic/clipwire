# ADR-0003: タイムアウトと監査ログ

- Status: Proposed (改訂: Opus レビュー反映)
- Date: 2026-09-30
- Depends on: ADR-0009(kill/キャンセル), ADR-0010(ハッシュ/承認レコード)

## Context

`exec` にタイムアウトがなく、ハングしたスクリプトがリクエストとスレッドを占有し続ける。Tailscale 越しに任意コードを実行できる以上、いつ・誰が・何を実行したかの記録も要る。

## Decision

### タイムアウト

1. target 定義に `timeout`(例 `"10m"`)を追加。**未設定なら実行時に 30 分を適用する**(保存・ハッシュ計算には補完しない。ADR-0010)。`exec --timeout <dur>` はクライアントからの**短縮のみ**可能(延長は、承認済み定義の上限を回避できるため不可)。
2. タイムアウト時は ADR-0009 の方式で Job Object をツリーごと終了し、終了コードを `124`、状態を `timeout` とする。
3. 純 Rhai ループは `on_progress`、`sleep` は 100ms 刻みのキャンセル確認、`run` は Job kill で戻す(ADR-0009 §4)。本 ADR は期限の判定のみを持つ。
4. `timeout` は承認対象内容(ADR-0010 の正規形)。
5. **移行**: 既存ターゲットは、これまで無期限だったため、30 分超を要するもの(および `cmd /c start` 形式で常駐アプリを起動するもの。後者は ADR-0009 §3 により main 終了で running が終わるため影響を受けにくい)は、導入時に全 registered を点検し、必要なら明示的に `timeout` を設定する。

### 監査ログ

6. `%APPDATA%\clipwire\audit.jsonl` に追記する(監査ログと承認レコードは小さくローミングしても害がないため `%APPDATA%`、ジョブログは大きくなりうるため `%LOCALAPPDATA%`)。フィールド: 時刻、イベント(`register` / `approve` / `deny` / `start` / `end` / `kill` / `timeout`)、`job_id`、ターゲット名、**定義ハッシュ**(本文は `approved/<hash>.json` で復元できる。ADR-0010)、要求元 IP、引数(ADR-0004。値をそのまま記録)、終了コード、所要時間。
7. **記録しないもの**: トークン、環境変数の値、スクリプト出力(出力はジョブログが保持し、保持期間が別)。
8. ローテーション: 10 MiB 超で `audit.1.jsonl` に退避(1 世代)。書き込み失敗は exec を止めず `tracing::error!` に出す。承認系(`register` / `approve` / `deny`)の記録失敗は警告トーストも出す。
9. 閲覧は Windows 側 CLI(`clipwire audit --tail N`、ファイルを直接読む)のみ。リモート向けの `GET /audit` は提供しない(リモートから監査を読む必要性が薄く、露出を増やすだけ)。

### トークンの扱い

10. 子プロセス環境からの `CLIPD_TOKEN` 除去は ADR-0009 §5、サーバ自身の `remove_var` とトークンの読み込みは ADR-0011 §10 に従う。これは**事故防止**(子がうっかりログへ出す)であり、セキュリティ境界ではない(同一ユーザーの子プロセスは親のコマンドライン・環境ブロックを読める)。

## Consequences

- ハングしたジョブが資源を占有し続けなくなる。
- 監査に残るハッシュから承認時点の本文を復元でき、事後調査・差分確認ができる。
- 30 分の暗黙上限は、既存の長時間ターゲットの挙動を変えうるため、移行点検が必要。
- 監査ログは追記専用ファイルだが、Windows 側管理者には改ざん可能。耐改ざん性は目標にしない。

## Alternatives considered

- **タイムアウトをクライアント側のみで実施**: クライアント切断でサーバ側は止まらない。
- **Windows イベントログへ出力**: 依存と権限が増える。将来の拡張候補。
